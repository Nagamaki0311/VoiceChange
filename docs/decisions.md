## D-001: 入力と出力を別々のAudioIODeviceとして開く

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は入出力デバイス間のクロックずれ補正（リングバッファ + 可変レートリサンプリング）と、サンプルレート差の吸収を求めている。

### 決定
- `juce::AudioDeviceManager`の一体型デバイスを使わず、`AudioIODeviceType::createDevice(出力名, "")`と`createDevice("", 入力名)`で2つのデバイスを開き、別々のコールバックで動かす。DSPは出力コールバック内で出力レートで行う。

### 理由
- JUCE 9.0.2のWASAPI実装（`juce_WASAPI_windows.cpp`）は、入出力一体型のとき1スレッドで両方を回し、共通のサンプルレートを要求する（共通レートがないと`open()`がエラーを返す）。低遅延モードではOS側のレート変換も無効になる。この構成ではクロックずれを補正する場所がない。
- DSPを出力側で行うと、処理時間の揺れがリングバッファで吸収され、出力の締め切りに対して必要なサンプル数だけを処理できる。

### 影響
- デバイスの一覧取得・開閉・エラー処理をアプリ側で実装する必要がある（AudioDeviceManagerの機能を使わない）。

## D-002: ピッチシフターをチェーン先頭に置き、不要時は休止する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は処理順を「層2 → 層1」とし、ピッチシフトのみ層1と層2を合算して1回で処理するとしている。位置は明記されていない。
- 48kHz・Signalsmith Stretchの実測で、移調の有無にかかわらず1コアの約1.5%を使う（Xeon 2.1GHz、ブロック20〜120ms）。ノーマル時1%未満の要件を満たせない。

### 決定
- シフターをチェーン先頭に置き、合計移調量0かつフォルマント係数1のときは休止する。休止⇔稼働は20msのクロスフェードでつなぐ。休止中は遅延がシフター分だけ短くなる（遅延は一定にしない）。

### 理由
- 単声の信号の方がシフト品質が良い、ロボットの変調周波数が層1ピッチで変わらない、ケロケロの補正量を加工前の声から求められる。
- 遅延を一定に保つ案（休止中も同じ長さの遅延線を通す）も検討した。OBSで音声のオフセットを固定値で合わせる用途では一定の方が扱いやすいが、変動幅は最大40ms程度で、プリセット切り替え時にしか変わらない。通話・自分の声のモニタリングでは短い方が有利なため、短くする方を選んだ。どちらの案も切り替え用の状態遷移が必要で、実装量は同程度。

### 影響
- 表示レイテンシはプリセットと層1ピッチで変わる。

## D-003: ブロック長をデバイス遅延から毎回計算する

- 日付: 2026-09-28
- 状態: 廃止（後継: D-014）

### 背景
- 原指示は「50ms以内に収まる最も長い設定を採用する」としている。Signalsmith Stretchの遅延はブロック長にほぼ等しい（実測）。一方、デバイス遅延は低遅延モード対応の有無で数ms〜20ms以上と大きく変わる。

### 決定
- デバイスを開いた時点で、ブロック長 = clamp(50ms − デバイス遅延 − リングバッファ目標 − 2ms, 20ms, 40ms) とする。

### 理由
- 固定値では、低遅延モード非対応のデバイス（VB-CABLE等が該当する可能性がある）で50msを超えるか、対応デバイスで品質を余らせる。20msの下限は男性の声の基本周期の2周期分を窓に含めるため。

### 影響
- 環境によっては50msを超える。その場合はUIに表示し、実測値を報告する。

## D-004: 開発環境での検証範囲

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 開発はLinuxのクラウド環境で行い、Windows実機・オーディオデバイスがない。

### 決定
- DSPコアとリングバッファのロジックを、JUCEのGUI・デバイス部から分離したライブラリにし、Linuxで単体テスト（オフライン模擬を含む）を行う。アプリ本体もLinuxでコンパイルし、Xvfb上でUIのスクリーンショットを確認する。
- Windowsの.exeはGitHub Actions（windows-latest、MSVC、`/MT`）でビルドし、同じテストをWindowsでも実行する。
- 実機での動作・聴感・1時間連続動作はユーザーが行う。判定用に統計ログを出力する。

### 理由
- 実機がない状態で「動作確認済み」とできる範囲を、合否を返すチェックで最大化するため。

### 影響
- WASAPI固有の挙動（低遅延モードの可否、デバイス抜去時の通知）は実機でしか確認できず、未検証として報告する。

## D-005: DSPコアをINTERFACEライブラリにする

- 日付: 2026-09-28
- 状態: 採用

### 背景
- JUCEモジュールはINTERFACEライブラリで、リンクしたターゲットごとにJUCEのソースがコンパイルされる。DSPコアをSTATICライブラリにすると、JUCEのソースがライブラリとexeの両方でコンパイルされ、重複定義やODR不一致の危険がある。

### 決定
- `vc_core`をINTERFACEライブラリにし、DSPソースとjuce_core/juce_audio_basics/juce_dsp/signalsmith-stretchをINTERFACEで持たせる。アプリとテストがそれぞれリンクする。

### 理由
- テスト実行ファイルはvc_coreしかリンクしないため、DSPソースがGUI・デバイスのヘッダをincludeするとテストのビルドが失敗し、層の分離が機械的に担保される。代償はDSPソースを2回コンパイルすることだけで、ファイル数が少ないため許容できる。

### 影響
- docs/spec.mdの「DSPコアを静的ライブラリにする」記述をINTERFACEライブラリに改める。

## D-006: リングバッファの充填量は読み出し直後に測る

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 読み出し前に測って目標 = max(Bi, Bo) + 2ms で制御すると、Bi ≈ Bo のとき読み出し前の充填量の最小値が1回の読み出し量を下回り、起動直後にアンダーランが数回起きる。

### 決定
- 充填量は出力コールバックの読み出し直後に測る。表示するリングバッファ遅延は「平滑化した読み出し直後の充填量 + Bo/2」（時間平均）とする。目標の式は仕様のまま据え置く。

### 理由
- 読み出し直後に測れば最小値 ≥ max(Bi, Bo) − Bi/2 + 2ms > 0 が保証される。目標の式は必要最小値よりBi/2ほど保守的だが、実機のスケジューリングの揺れが未測定のため余裕を残す。

### 影響
- 実機ログでアンダーランが0のまま推移するなら、目標を下げる余地がある。

## D-007: 出力段のリミッターをCompressorとクリップで構成する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- `juce::dsp::Limiter`は常に閾値-10dB・4:1の圧縮とメイクアップをかけ、ゲイン0dBでも小さい音を約+2.9dB持ち上げる。原指示の「ゲインを上げても0dBFSを超えないための簡易リミッター」は、通常時に音を変えない透過的なものを意図している。

### 決定
- `juce::dsp::Compressor`（閾値-1dB、比100、アタック0.1ms、リリース100ms）の後に`FloatVectorOperations::clip`で±1.0に制限する。

### 理由
- どちらもJUCEの既存部品で、閾値以下では音を変えず、クリップで0dBFSを超えないことが保証される。

### 影響
- 閾値を超える瞬間のアタック内はクリップが働くため、極端に大きな入力では歪みが出る。音割れよりは小さい。

## D-008: リバーブの混合量はJUCEの内部倍率を打ち消して渡す

- 日付: 2026-09-28
- 状態: 採用

### 背景
- `juce::Reverb`はdryLevelに×2、wetLevelに×3の内部倍率を掛ける。「wet = r、dry = 1 − r」をそのまま渡すと、r ≈ 0 でdryが+6dBになる。

### 決定
- `Parameters`には wetLevel = r/3、dryLevel = (1 − r)/2、width = 1 を渡す。仕様の「wet = r、dry = 1 − r」は出力に掛かる線形ゲインとして解釈する。

### 理由
- 仕様の意図（rで残響の混合量だけが変わり、r = 0で原音と同じ音量）を実現する変換であり、仕様変更ではない。

### 影響
- なし。

## D-009: デバイス異常時の扱いと多重起動

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は切断時のエラー表示と復帰時の再接続を求めているが、片方だけの異常、起動時に保存済みデバイスがない場合、多重起動について記載がない。

### 決定
- 片方のデバイスだけが異常になっても両方を閉じ、両方が揃ってから両方を開き直す。
- 起動時に保存済みのデバイスが見つからない場合は既定デバイスへ切り替えず、エラーを表示して再試行を続ける。
- 多重起動を禁止する（`moreThanOneInstanceAllowed() = false`）。

### 理由
- 両方を閉じる方式は状態の組み合わせが減り、クロックずれ補正の再初期化も1か所で済む。
- 保存済みデバイスへの自動復帰を優先するため、勝手に既定デバイス（物理スピーカー等）へ声を流さない。配信中に意図しない出力先へ声が出る事故を防ぐ。
- 多重起動するとデバイスを二重に開き、同じVB-CABLEへ2系統の音が混ざる。

### 影響
- 保存済みデバイスを使わなくなった場合は、利用者がドロップダウンで選び直す必要がある。

## D-010: 最終出力の異常値検査はバイパス中も行う

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 仕様ではバイパス時に処理チェーン全体（NaN検査を含む）を入力の素通しに置き換える。入力デバイス側から異常値が来た場合に検査がなくなる。

### 決定
- 最終出力の非有限値検査はバイパス中も常に行う。エラー表示は docs/design.md 6章に従い、異常値は10秒間、デバイス異常は復旧まで表示する。

### 理由
- 検査のコストは1ブロックの走査だけで、VB-CABLE経由で配信・通話アプリへ異常値を渡す事故を防げる。

### 影響
- なし。

## D-011: 利用形態は個人利用のみ（配布なし）

- 日付: 2026-09-28
- 状態: 採用

### 背景
- JUCE 9はAGPLv3と商用ライセンスのデュアルライセンスで、exeを第三者へ配布する場合はソースのAGPL公開かJUCEのライセンスが必要になる。

### 決定

## D-012: リングバッファの充填量は入力ブロックの到着位相に依存しない連続換算値で制御する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- T-003の1時間模擬で、入出力のブロック長が近い構成（48kHz・480サンプル同士など）では、平滑化した充填量が約100秒周期で1ブロック分跳ねる鋸歯状になり、「目標±25%に収まる」条件を満たさなかった。
- 原因は、出力の読み出し時点から見た入力ブロック到着の位相が T = Bi/(fs×ずれ) の周期でゆっくり一周するため。読み出し直後の生の充填量が位相に応じて1ブロック分変わり、平滑化の時定数（2秒）より遅いため平均で消えない。模擬の人工物ではなく、実機でも起きる。

### 決定
- 入力を連続的に到着したとみなす連続換算充填量 fill_c = 生の充填量 − 直前の入力ブロック長 + fs_in × (現在時刻 − 直前のpush時刻)（上限は直前のブロック長）で平滑化・速度比制御・再充填判定・超過判定を行う。アンダーラン判定は生の充填量のまま。
- push/pullに単調時計の時刻を渡す。表示する遅延は「平滑化したfill_c + (Bi + Bo)/2」とする。
- 目標充填量の式と合格条件の閾値は変えない。

### 理由
- 生の充填量は常に fill_c 以上なので、fill_cを目標に保てばアンダーランへの余裕は従来と同じかそれ以上になる。遅延予算を増やさずに位相由来の揺れだけを取り除ける。
- 目標を大きくする案（例: 40ms）は50msの遅延予算と両立しない。判定基準を緩める案は、実機で速度比が不要に振れる問題を残す。

### 影響
- 入力コールバックの時刻が揺れると fill_c に揺れが乗るが、平滑化で吸収される（S7のジッタ0〜3msで確認する）。

## D-013: Signalsmith Stretchの移調精度はD-003のブロック長（20〜40ms）では±1%を保証できない

- 日付: 2026-09-28
- 状態: 解決済み（対応はD-014）

### 背景
- docs/plan.md P3（移調精度: 220Hz正弦、FFTピークが期待値の±1%）が、`configure(1, 960, 240)`（20ms、D-003の下限）で実装したPitchShifterで不合格になった（測定誤差2.8〜3.9%）。PitchShifter/Engineのラッパコードのバグを疑い、Signalsmith Stretch単体を直接呼ぶ独立の再現コード（`/tmp/.../scratchpad/probe2/probe*.cpp`、ゼロクロス法で周波数を実測、JUCE非依存）で同一条件を再現したところ、ラッパを介さない生のライブラリ呼び出しでも同水準の誤差（220Hz・±12/±5/+8/-6半音で2.5〜3.6%、`setFormantFactor`のcompensatePitchフラグの有無に依存せず同じ値）が再現した。
- ブロック長を伸ばすほど誤差は縮む（block=960→2.8〜4.2%、block=1920(D-003上限40ms)→0.0〜2.5%、block=4096→0.45%）が、D-003の上限40ms（block=1920）でも6ケース中2ケースが±1%を超えた。誤差はブロック長のFFTビン幅（fs/block、960なら50Hz）に対する入力周波数のビン整合度と強く相関し（ビン整合が良いほど誤差が小さい）、`setFormantFactor`の有無に依存しない。以上から、Signalsmith Stretchのピーク追跡による周波数マッピングが、この帯域幅では入力周波数とSTFTビン格子の位置関係に応じた数%の量子化的な誤差を生む、という物理的な限界であり、PitchShifter/Engineのバグではないと判断した。
- 合成母音を使うP4（層1ピッチでのフォルマント保持、f0比・包絡スケールs）も同時に不合格（f0比誤差最大約11%、s=1.335/2.0）。母音のf0(100Hz)はテスト対象の正弦(220Hz)よりもビン幅(50Hz)に対して相対的に低く粗いため、同一原因でより大きく現れたと考えられる。

### 決定
- 未決定。閾値（±1%）・実装（PitchShifterの状態遷移・ブロック長決定式）はいずれも変更していない。P3・P4は実測値付きで不合格のまま報告し、Manager/Plannerの判断を仰ぐ。

### 理由
- AGENTS.mdの方針（「合格しない場合は閾値を緩めずに原因を直す。計画の閾値が不適切だと判断した場合は根拠を添えて報告し、勝手に変えない」）に従い、根本原因（ライブラリのSTFT分解能に起因する周波数量子化）を独立再現コードで特定した上で、閾値・実装の変更はManager判断に委ねる。

### 影響
- 選択肢（例）: (a) P3/P4の許容誤差をブロック長依存で緩める、(b) ブロック長の下限をP3合格に必要な値まで引き上げる代わりに遅延予算(D-003の50ms)を見直す、(c) T-005で検討予定の「PSOLA系への差し替え」をピッチシフター全体に前倒しで適用する、(d) 現状を許容し実機の聴感評価に委ねる。T-005のF1〜F3（フォルマント測定）でも同種の問題が再燃する可能性が高く、T-005着手前にこの判断を確定させることを推奨する。

## D-014: ピッチシフターのブロック長を120msに固定し、50ms目標はシフター休止時に適用する

- 日付: 2026-09-28
- 状態: 採用（D-003を置き換える）

### 背景
- D-013のとおり、Signalsmith Stretchはブロック長20〜40msでは移調後の音程が1〜5%ずれる（220Hz・200Hzの正弦で実測。Managerがライブラリ単体で再現確認済み）。120msでは誤差0.6%以内に収まる。
- ユーザーに「PSOLA方式への差し替え」「Signalsmithのまま基準を緩める」「Signalsmithのままブロック長を延長」の3案を示し、ユーザーがブロック長の延長を選んだ。

### 決定
- ブロック長は120ms、インターバルは30ms（Signalsmith Stretchの`presetDefault`相当）に固定する。`decideStretchBlock`（デバイス遅延からの計算）は廃止する。
- 50msの遅延目標は、ピッチシフターが休止している経路（ノーマル・エコー・ロボット・トークボックスで層1ピッチ0）に適用する。シフター稼働中の遅延は約120ms + デバイス・リングバッファ分（合計おおむね130〜160ms）になることを仕様として受け入れる。
- UIの遅延超過警告（design.mdのW2）は、シフター分を除いた遅延（デバイス入出力 + リングバッファ）が48msを超えたときに出す。
- 移調精度の合格基準（P3・P4の±1%）は変えない。

### 理由
- 音程の正確さを優先した（ユーザー判断）。特にケロケロは最寄りの半音に正確に合わせる効果で、数%のずれは目的を損なう。
- シフター休止の仕組み（D-002）により、音程を変えないプリセットでは遅延が増えない。

### 影響
- 音程・声質を変えるプリセット（ヘリウム・ミニオン・ジャイアント・ケロケロ、および層1ピッチ≠0）では、配信・通話で声が遅れて聞こえる。OBSでは映像との同期のため音声オフセットの調整が必要になる場合がある。READMEに記載する。
- シフター休止⇔稼働の切り替え時に120ms分の音が重複・欠落する（D-002の帰結。クロスフェードでクリックは防ぐ）。

## D-015: 低い基本周波数（f0=100Hz付近）でのフォルマント追従誤差はSignalsmith Stretchの既知の特性として受け入れる

- 日付: 2026-09-28
- 状態: 採用

### 背景
- D-014（ブロック長120ms固定）の適用後、P3（220Hz正弦、±12/±5/+8/-6半音）は全6ケースが±1%以内（実測0.04〜0.85%）に収まり合格した。
- 一方P4（合成母音f0=100Hz、/a/、±5半音）は不合格のまま: +5半音は包絡スケールs=1.165（許容[0.9,1.1]を超過。f0比は合格）、-5半音はf0比0.759707（期待0.749154、誤差+1.41%で不合格）・s=0.795（許容範囲外）。
- Managerの指示により、P4側の測定器（`measureFundamentalHz`/`measureFormantEnvelope`/`measureEnvelopeScale`、いずれもtests/TestSignals.h）のバグの可能性を疑い、独立の再現コード（PitchShifter/Engine・自作の解析関数のいずれも介さない、生のSignalsmith Stretch + 高精度ゼロクロス法という別の計測手段）で検証した。100Hz純音を-5半音シフトした場合、独立コードでも+1.395%の誤差（P4の測定値75.9Hzとほぼ一致する75.96Hz）を確認した。同条件で150Hz(-5半音)は+0.111%、220Hz(-5半音)は+0.252%、100Hz(+5半音)は+0.637%と、誤差は「基本周波数が低いほど・シフト方向によって」大きくなる非対称な傾向を示した。
- 以上より、P4不合格の原因はSignalsmith Stretchが120msブロックでも低い基本周波数（100Hz、48kHzで约12バンド目相当の低域）ではなお数%規模のピッチ量子化誤差を残す、という残存するライブラリ特性であると判断した（tests/TestSignals.hの測定コードは独立再現コードと同じ値を示しており妥当と確認できた）。包絡スケールsのずれ（f0比の誤差1.4%よりずっと大きい17〜21%）は、`setFormantFactor(1.0, true)`のフォルマント補償がStretch内部の基本周波数推定（`estimateFrequency()`）に依存しており、その推定も同じ低域不正確さの影響を受けて増幅された可能性を仮説として挙げた。

### 追加実験: setFormantBase(真のf0)の効果検証
- 上記仮説（フォルマント補償の内部f0推定が原因）を検証するため、テスト内の一時コード（`tests/FormantBaseExperimentTemp.cpp`、検証後に削除済み）で、Signalsmith Stretchへ`setFormantBase(真のf0)`を明示的に与えた場合と与えない場合（デフォルトの自動推定）を比較した。f0=80/100/150Hz、±5半音の組み合わせで測定した結果は次のとおり（f0比誤差%、包絡スケールs）:

| f0(真値) | 半音 | 自動推定(既定) | setFormantBase(真のf0) |
|---|---|---|---|
| 80Hz | -5 | 誤差+1.246%, s=0.780 | 誤差+1.110%, s=0.750 |
| 80Hz | +5 | 誤差+0.927%, s=1.190 | 誤差+1.078%, s=1.310 |
| 100Hz | -5 | 誤差+1.409%, s=0.795 | 誤差+1.373%, s=0.750 |
| 100Hz | +5 | 誤差+0.643%, s=1.165 | 誤差+0.720%, s=1.310 |
| 150Hz | -5 | 誤差-0.216%, s=0.995 | 誤差-0.281%, s=0.750 |
| 150Hz | +5 | 誤差+0.741%, s=1.010 | 誤差+0.441%, s=1.305 |

- f0比の誤差は`setFormantBase`の有無でほぼ変わらない（差は0.1%程度）。これはピッチ量子化誤差が周波数マッピング（`mapFreq`/`findPeaks`/`outputMap`）由来で、フォルマント処理（`updateFormants`）とは別経路のため妥当な結果である。
- 包絡スケールsは、自動推定では150Hzでほぼ完璧(0.995〜1.010)になる一方、`setFormantBase`で真のf0を明示すると-5半音は常にs≈0.75、+5半音は常にs≈1.31付近に張り付き、f0(80/100/150Hz)によらずほぼ同じ値になる。これは真のf0を与えるとむしろ悪化する、当初の仮説（自動推定の誤りが原因）と逆の結果である。Stretch内部の`updateFormants()`は`freqEstimate`（推定f0のバンド番号）を使って`formantMetric`のスムージング減衰率を決めており、真のf0（80〜150Hzはバンド番号にして10〜18程度の低い値）を直接使うと減衰が強くなりすぎて包絡が過度に平滑化される可能性がある。自動推定（`estimateFrequency()`、コード上「VERY rough」と明記）はこの値とは別の基準（スペクトル上位ピークの間隔）を返しており、結果的に100〜150Hz帯ではこちらの方が実用上のsを安定させている。

### 決定
- ユーザーがSignalsmith Stretchの継続使用を選択したため、低域でのフォルマント追従・移調誤差はライブラリの特性として受け入れ、閾値を緩める代わりにP4を合格基準と特性確認の2本へ分割する（`PitchShifter`・`Engine`本体の実装は変更しない）。
  - P4a（合格基準）: 合成母音f0=150Hz、±5半音。f0比±1%、包絡スケール s = 1.0±10%（従来どおりの厳格な基準）。
  - P4b（低い声の特性確認）: 合成母音f0=100Hz、±5半音。f0比±2%、包絡スケール s = 1.0±25%。実測基準値（f0誤差最大+1.4%、s=0.795(-5半音)/1.165(+5半音)）をコメントに明記し、これより悪化したら回帰として検出する。
  - T-005のF1〜F3（ヘリウム・ミニオン・ジャイアント）も同じ方針とし、f0=150Hzを合格基準にする。f0=100Hzでの特性確認もあわせて測定し、悪化していないかを報告する（失敗判定にはしない）。
- `PitchShifter`へ`setFormantBaseHz`等のAPIは追加しない（上記実験のとおり、真のf0を明示してもsは改善せずむしろ悪化するため）。

### 理由
- f0=150Hzでは包絡スケールsがほぼ1.0（0.995〜1.010）に収まり、仕様どおりの精度を満たせることを実測で確認した。一方f0=80〜100Hzの低い声では、移調に伴いフォルマントが移調方向へ約17〜21%（s=0.75〜1.31相当）追従し、f0自体も最大1.4%（約24セント）ずれる。これはSignalsmith StretchのSTFT分解能に起因する残存特性で、実装のバグではないと独立再現コードで確認済みである（D-013・D-015の背景・追加実験参照）。
- ユーザーはSignalsmith Stretchを継続する方針を選んだため、この特性を仕様として受け入れる。回帰を検出できるよう、閾値を無条件に緩めるのではなく、実測基準値をコメントに残したP4bとして分離し、これより悪化した場合にのみ問題として顕在化するようにする。

### 影響
- 低い男性の声（f0=80〜100Hz程度）で層1ピッチ（またはヘリウム・ミニオン・ジャイアント等の移調プリセット）を使うと、声質（フォルマント）がわずかに移調方向へ動く。READMEに既知の制限として記載する。
- T-005のF1〜F3もP4a/P4bと同じ方針（f0=150Hzを合格基準、f0=100Hzを特性確認）で実装する。
- `setFormantBase`によるフォルマント補償の改善は選択肢から除外する（実験で効果なしと確認済み）。ピッチ検出器（T-005）の出力をシフターへ渡す配線自体はケロケロ機能に必要なため別途実装するが、P4の改善目的では行わない。
- T-005追記: ヘリウム（移調0・フォルマント係数1.6）でも`setFormantBase`（真のf0・ピッチ検出器の推定値のいずれも）はs=1.000となりフォルマントが全く動かず、既定（f0=80/100/150Hzでs=1.075/1.070/1.585）より悪化する。低い声でヘリウムが効きにくいのはライブラリの限界として受け入れる（README参照）。

## D-016: T-007のエラー分類・単一消費者化・無言終了の判定

- 日付: 2026-09-28（レビュー指摘への対応で2026-09-28に改訂）
- 状態: 採用

### 背景
- plan.md「AudioIO」「ConnectionMonitor」節は監視ロジックの骨格のみを定義しており、実装時に以下の判断が必要だった。レビューで、初版の「無言終了は`audioDeviceStopped()`で拾える」という前提と、E4/E3の切り分けがdesign.md 6.1/6.2節と食い違っていることが判明したため改訂した。

### 決定
1. **E4（デバイスを開けない）とE1〜E3（切断・再接続中）の切り分け**: `AudioIO`が「現在の`open()`世代で一度でもstartまで成功したか」を持つ。`open()`（起動時・手動選択時）が世代を進め、ConnectionMonitorのTryReopenによる再試行は世代を進めない。一度もstartに成功していない世代の失敗は、時間が経ってもE4（`AudioIO::getFailedSide()`が返す失敗側None/Input/Output/Bothの行を赤枠、文言も失敗側で決める。文言の前方一致には頼らない）。startに成功した後の異常だけがE1〜E3で、保存デバイス名が一覧から消えていればE1/E2、消えていなければ（ドライバが一覧に残ったまま無言で止まった場合等）E3として両方の行を赤くする。再接続の再試行はどちらの場合も2秒ごとに続ける（開くこと自体の失敗は`ConnectionMonitor::enterFailed()`で異常状態へ入れる）。
2. **Engineのエラーフラグ（bit0非有限値・bit1例外）は`AudioIO`の500msタイマーだけが読んで消費する**: T-006まではMainComponentが直接`engine.getErrorFlags()`/`clearErrorFlags()`を読んで10秒間のE5表示を管理していたが、T-007でトレイのバッジ・ツールチップも同じ情報を必要とするようになった。2箇所が同じedge-triggeredフラグを消費すると早いもの勝ちで取りこぼす。`AudioIO`が唯一の消費者になり、`hasRecentEngineError()`（レベル判定）と`getLastEngineErrorTimeText()`を公開する形に変更した。
3. **異常の検出経路は2つ（即時経路とコールバック回数の停滞）**: JUCE 9のWASAPIは、デバイス抜去・セッション失効（`flagShutdown`）やサンプルレート変更を検出すると`handleAsyncUpdate()` → `close()` → `stop()` → `audioDeviceStopped()`をメッセージスレッドで呼ぶ。`AudioIO::close()`内の意図した`stop()`（`expectingIntentionalStop`）以外で`audioDeviceStopped()`が呼ばれた場合は`deviceStoppedFlag`を立ててエラーフラグへ合成し、抜去・レート変更を即時に検出する。呼ばれないのは、入力専用スレッドが1秒のイベント待ちタイムアウトで通知なしに終了する無言終了だけである。これはコールバック回数の停滞で検出する。ConnectionMonitorは入力・出力それぞれの最終進捗時刻を持ち、どちらか一方でも2秒進まなければ異常とする（片方だけ止まる異常を、もう一方が進んでいることで見逃さない）。
4. **開き直しの試行は最小限にする**: `openDevices()`は入力が開けなければ出力を開かない（失敗側は出力名が一覧にあるかでInput/Bothを決める）。再試行（TryReopen）で開き直すのは、両方の名前が一覧にあるときだけで、無いときは一覧の変化（即TryReopen）を待つ。入力切断中に2秒ごとに出力デバイス（低遅延モード）を開閉しないため。

### 理由
- 1: E4は「今すぐ別のデバイスを選ぶ必要がある」状態、E1〜E3は「待てば戻る」状態であり、一度も動いていないデバイスに「再接続中」と出すのは誤り。世代のフラグにより、ConnectionMonitorのインターフェースを大きく変えずにdesign.mdの表と一致させられる。
- 2: エラーフラグの消費者を1つに絞ることで、取りこぼし・二重クリアの競合を構造的に防げる。
- 3: 実際のJUCE 9のソース（`juce_WASAPI_windows.cpp`の`handleAsyncUpdate()`・`stop()`・入力スレッドの1秒タイムアウト）で、抜去・レート変更ではコールバックが呼ばれ、入力スレッドの無言終了では呼ばれないことを確認した。後者で検出できる情報はコールバックが進んでいるかだけである。

### 影響
- MainComponentの`errorUntilMs`/`errorTimestampText`は削除し、`AudioIO`側の値を読むだけにした。
- 実機でのデバイス抜去・再接続時のE1〜E3表示の切り替わりはWindows実機でのみ確認できる（README「手動確認手順」参照）。

## D-017: E9の無音からの発声開始は10msアタック付き入力で判定する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- plan.md E9は「デジタル無音から発声し始める瞬間も含める」56通りの切替クリック判定（隣接差最大値 ≤ 1.5 × max(切替前, 切替後の定常区間)）を求める。
- 振幅が瞬時に最大になる位相そろいの合成母音を無音から入れると、稼働中のシフターから helium/minion へ切り替わる6通り（helium/giant/kerokero→minion、minion/giant/kerokero→helium）が基準を超えた（minion→helium: 隣接差0.181、定常0.093、ピーク0.79対0.42）。ピークはシフター遅延（120ms）の位置に出る。
- Stretchの無音モード（入力エネルギー<1e-15が2ブロック続くと入力素通し）が原因と推定し、振幅1e-6の決定的ディザで避ける実装を試したが改善しなかった。無音部を-80dBFSの雑音にしても3通りが超過した。一方、発声開始に10msのアタックを付けると112通りすべてが通常基準で合格した。原因は無音モードではなく、位相がそろった瞬時の立ち上がりをSignalsmith Stretchが通すときの定常の約2倍のピークである。

- レビュー対応での再測定（切替位置を7・11サンプルずらし、切替直前のサンプルから判定した後）: 10msアタックは4条件とも最悪比1.297以下で合格（上限1.5）。0msアタックの参考値は、母音がゼロ交差から始まる場合（offset 0、入力自体に段差なし）で最悪比1.944（minion→helium）、母音の途中から始まる場合（offset 7）は入力自体に段差があり最悪比5.847（normal→minion。Priming中は加工前の声がそのまま出るため入力の段差そのもの）。結論（瞬時の立ち上がりではシフター経由で定常の約2倍が出得る。実声には数ms以上のアタックがある）は変わらない。

### 決定
- E9の無音からの発声開始ケースは、立ち上がりに10msの二乗余弦アタックを付けた入力で判定する。112通りすべてを通常基準（1.5倍）で判定し、「既知」扱いは設けない。ディザは採用しない。

### 理由
- 実際の声の立ち上がりは数ms以上かかり、振幅が瞬時に最大になる位相そろいの合成母音は現実の入力を代表しない。

### 影響
- 瞬時に最大振幅で立ち上がる入力（位相がそろった信号）では、稼働中のシフター経由の切替時に定常の約2倍の段差が出得る。実声では通常発生しない想定で、実機の聴感確認（README「手動確認手順」）に委ねる。

## D-018: バイパス時も出力を±1.0にクリップする

- 日付: 2026-09-28
- 状態: 採用

### 背景
- T-008のLongRunで、バイパス中にピークが1.0を超えた。バイパス（完全バイパスと20msのクロスフェード区間）はリミッターを通らず、ResamplingFifoのLagrange補間後の入力がそのまま出る。補間のオーバーシュートにより、クリップ済みの入力（ホットマイク）で1.0126、0dBFS一杯の広帯域雑音で最大1.36が出力へ出た。docs/spec.mdの検証方針は「出力が0dBFSを超えないこと」を求める。

### 決定
- Engineのバイパス経路（完全バイパスとクロスフェード区間の両方）の最終出力の直前で、`FloatVectorOperations::clip (buf, buf, -1.0f, 1.0f, n)`を掛ける。リミッター（コンプレッサー）は通さない。

### 理由
- 最終出力の非有限値検査（D-010）と同じ位置付けで、バイパス中も出力の安全性だけは保つ。|x|≤1の入力はビット一致のままで、E4a（完全バイパスはビット一致）を保つ。コンプレッサーを通すとバイパスの透過性が失われるため、クリップのみとする。

### 影響
- バイパス時に|x|>1になる入力（補間のオーバーシュート等）は±1.0に切り詰められる（通常の音では起きない）。tests/EngineTests.cppのE4cで確認する。

## D-019: ノイズ除去にRNNoise v0.2（組み込みモデル）を採用し、自前のCMakeターゲットでビルドする

## D-020: マイク処理（ノイズ除去→EQ）を層1・層2の前に置き、全体バイパスの対象外にする

- 日付: 2026-09-29
- 状態: 採用（ユーザー確認済み）

### 背景
- ノイズ除去とEQはSonarの置き換えで、声を変える効果とは性格が違う。全体OFFは「緊急で原音に戻す」操作として設計されている（design.md 2章）。

### 決定
- 処理順は 入力 → ノイズ除去 → EQ → 既存チェーン とする。ノイズ除去とEQはそれぞれ独自のON/OFFを持ち、全体OFFでは外さない。バイパスの解除時にマイク処理はリセットしない。非有限値の検出時はリセットする。ノイズ除去・EQとも初回起動時はOFFとする。

### 理由
- EQをノイズ除去より前に置くと、EQで持ち上げた帯域の雑音まで増幅してからノイズ除去へ渡すことになる。
- Sonarを経由していたときも、本アプリのOFFではSonarの処理が残っていた。全体OFFでマイク処理まで外すと、OFFにした瞬間に雑音の多い生音が配信に乗る。
- 初回起動時にOFFとするのは、Sonarを経路に残したまま使っている間の二重処理を避けるため。

### 影響
- 「完全バイパスはビット一致」（E4a）は、マイク処理がOFFのときに限る。バイパス中の表示文言をマイク処理の状態で出し分ける（design.md 6章）。
- バイパス中はEQで持ち上げた信号がリミッターを通らず、±1.0のクリップだけになる（D-018）。

## D-021: 48kHz以外の出力レートでは、RNNoiseの経路だけを固定比のLagrange補間で48kHzに変換する

- 日付: 2026-09-29
- 状態: 採用

### 背景
- RNNoiseは48kHz固定。Engineは出力デバイスのレート（WASAPI低遅延モードではミックスフォーマットのレート）で動き、アプリ側で選べない。

### 決定
- 出力レートが48kHz以外のときは、RNNoiseの前後に固定比の`juce::LagrangeInterpolator`を置く。原音側の経路は変換しない。
- 代替案: WindowedSinc（品質は高いが片道100サンプルの遅延と約200点の演算）、48kHz以外ではノイズ除去を無効にする（出力デバイスによって機能が消える）、44.1kHzをそのまま48kHzとして渡す（帯域の割り当てがずれ、品質を評価できない）。

### 理由
- 既存のリングバッファのレート変換と同じ部品で、遅延（数サンプル）とCPUが小さい。声の帯域では高域の減衰は小さい（推測。T-010のN6とN3aで確認する）。

### 影響
- 44.1kHzでは原音側の遅延が整数サンプルに丸められ、混合時に1サンプル未満のずれが残る（混合する背景ノイズ0〜50%の範囲の高域でわずかに干渉しうる）。
- 往復（上げ＋下げ）のLagrange変換の減衰（T-010レビューの実測）: 44.1kHzで1kHz・5kHzが0.00/−0.01dB、10kHz −0.26dB、15kHz −1.75dB、18kHz −3.20dB、20kHz −3.94dB。96kHzで10kHz −0.08dB、15kHz −0.60dB、18kHz −1.29dB、20kHz −1.82dB。88.2kHzで10kHz −0.11dB、15kHz −0.83dB、18kHz −1.82dB、20kHz −2.66dB。声の帯域（〜5kHz）では減衰は無視できる。10kHz以上の空気感の帯域への影響は、実録音の評価（T-014・T-015）で確認する項目とする。

## D-022: ノイズ除去の強さは原音との混合とVAD連動の広帯域ゲートで作り、スペクトルゲートは作らない

- 日付: 2026-09-29
- 状態: 採用（ユーザー確認済み）

### 背景
- RNNoiseには強さの調整がない。ユーザー案は、RNNoiseに無声区間のスペクトルゲートを組み合わせるものだった。

### 決定
- 背景ノイズのスライダーで、0〜50%は遅延を揃えた原音との混合比、50〜100%は完全なRNNoise出力にVAD連動ゲートの減衰（最大18dB）を加える。

### 理由
- 帯域ごとの抑制はRNNoise自体が32帯域で行っている。無声区間に残る雑音の抑制は広帯域ゲートで足りる見込みで、FFT・雑音推定・オーバーラップ加算が要るスペクトルゲートより実装と調整が小さい（判定ラダー7の最小構成）。
- 1本のスライダーで「弱い→強い」が連続的に変わり、Sonarのスライダーと同じ感覚で使える。

### 影響
- 実録音の比較で、無声区間に音色のある残留雑音（ファンの唸り等）が目立つ場合は、スペクトル処理の追加を別途検討する。
- 低い声やささやきでVADが外れる場合に備え、原音のエネルギーによる開放条件とホールド200msを持たせる。
- 更新（T-011）: ゲートを閉じる側の余裕を雑音床+6dBから+8dBに変更した（開く条件は+12dBのまま、4dBのヒステリシス）。ピンク雑音は10ms窓のパワーが大きく揺れ、+6dBでは閉じるまでに1〜2秒かかり、ピンク雑音−30dBFSの7秒のうち閉じていたのは約40%だった（+8dBで発話後の無音の84%）。実録音の比較と聴感で再調整してよい。
- 既知の限界（T-011レビュー）: 雑音床は−90dBFSを下限に3dB/秒でしか上がらないため、デジタル無音を3秒続けた後に発話し、その後−60dBFSの雑音になると、ゲートが閉じるまで8.7秒かかる（最初から雑音があれば0.22秒）。実装は変えず、実録音で確認する（ミュート明けなど）。

## D-023: インパクトノイズはノイズ除去の遅延を先読みに使う時間領域の減衰で抑える

- 日付: 2026-09-29
- 状態: 採用

### 背景
- 打鍵・クリックの除去は「可能ならついで」で、発話と重なる打鍵の完全除去は目標にしない。

### 決定
- 原音で速い包絡と遅い包絡の比から短い音を検出し、その音が出力に届く2ms前から短く減衰させる。発話中は減衰量を半分にし、閾値を上げる。初期値は0%（停止）。

### 理由
- ノイズ除去は固定の遅延を持つため、追加の遅延なしに先読みができ、立ち上がりの速いクリックの頭も抑えられる。追加依存はない。

### 影響
- 子音・破裂音の頭を誤検出して削る可能性がある（テストN5bと聴感で確認する）。
- 更新（T-011）: ホールドを15msから3msに変更した。N5b（10msアタックの母音の立ち上がり、インパクト100%）で、15msでは立ち上がりの最初の数msの検出が母音のピークまで減衰を続けて−1.68/−1.32dB（閾値−1dB）になったため。ホールド3msで−0.84/−0.61dB。クリックの除去（N5a、背景70%）は3回が−18.9〜−19.9dB、5ms減衰のクリックも−15.5〜−16.3dB。ゲートが開いている間に来るクリックは減衰量が半分（12dB）になる点は変わらない。実録音の打鍵の聴感で再調整してよい。
- 更新（T-011レビュー）: 大きなクリック（ピーク-10dBFS、-70dBFS 雑音上）の3kHzでは、背景0/70/100%のすべてで12回中12回が−12.0dB（減衰量が半分）になる（レビューの追加プローブ。6kHzは7/12、1kHzは1〜3/12）。RNNoiseのVADがクリックに反応し、ゲートが出力より約10ms先行して開くため、インパクト抑制が「発話中」と判断するからで、「6回中1回」ではなく3kHzクリックでは系統的である。この設計上の限界は今回は設計変更せず、既定のインパクト0%のまま、実録音（T-014・T-015）で開放状態の統計と緩和策（VAD先行分だけ遅らせたゲート履歴の参照、検出比による半減の連続化など。破裂音のN5bと衝突しうる）を評価する。
- 更新（T-011レビュー）: ホールド3msは、合成信号（10msアタック）でN5bとN5aの成立域（2〜4ms）の下限側を選んだ暫定値で、実録音での再調整を前提とする。アタック20msの立ち上がりでは f0 100Hz −1.19dB（1dB超）、140Hz −0.76dB（参考ログ）で、アタック20ms以上の立ち上がりやVADが上がらない小声・ささやきでは、インパクト100%で1dBを超えうる。既定はインパクト0%。

## D-024: EQはJUCEのIIRで実装し、音声スレッドでは確保なしで係数を更新する

- 日付: 2026-09-29
- 状態: 採用

### 背景
- Sonarの設定を再現できるパラメトリックEQが必要。`IIR::Coefficients::make*`は参照カウントのオブジェクトを確保するため、音声スレッドでは使えない（plan.md 5章）。

### 決定
- `juce::dsp::IIR::Filter`を5段直列にする。係数は`IIR::ArrayCoefficients`（`std::array`）で計算し、`prepare()`で作成済みの`Coefficients`へ`operator=`で代入する。バンドのタイプはピーキング・ローシェルフ・ハイシェルフ・ローカット・ハイカットから選ぶ。

### 理由
- 既存の部品で足りる（判定ラダー3）。代入は容量が足りていれば再確保しない（JUCEのソースで確認。9.0.2でもT-012で確認）。

### 影響
- Sonarとフィルタの定義（Qの意味、カットの傾き）が違う場合は、換算が要る（T-015）。
- 更新（T-012）: JUCE 9.0.2のソースで確認した（`Coefficients::operator=(std::array)`は`clearQuick`＋`ensureStorageAllocated(max(8, Num))`、`Filter::reset()`は次数が同じなら再確保しない）。EQ5が確保0回（`new`と、glibcでは`malloc`も）。EQは`Filter::process()`ではなく`processSample`を使い、`snapToZero`を32サンプルのグループの終わりで行う（`process()`は呼び出しごとに`snapToZero`し、ブロックの区切りで状態の丸めが変わって分割処理のビット一致が崩れる）。

## D-025: ノイズ除去ON時の遅延とCPUの要件

- 日付: 2026-09-29
- 状態: 採用（ユーザー確認済み）

### 背景
- ノイズ除去は30ms（1440サンプル@48kHz）の固定遅延（480サンプル単位の処理と、RNNoiseの先読みを含む固有遅延960サンプル。T-009・T-010で実測）を加え、CPUも増える。現行の要件（シフター休止時50ms以下、ノーマル1%未満）はノイズ除去を想定していない。

### 決定
- 50ms目標の判定（W2）はデバイス入出力＋リングバッファのまま据え置く。ノイズ除去の遅延は50ms目標の外で加算し、内訳に「除去」として表示し、合計に含める。
- CPU要件: ノイズ除去・EQ OFF時は現行のまま。ON時の増分は1コアの3.5%以下を目標とする（2026-09-30、ユーザー承認。当初は3%以下としたが、T-012の実測［Linux Xeon 2.1GHz、ノーマル+2.8〜+3.0、トークボックス+2.1〜+2.4、ミニオン+3.2〜+3.5ポイント］でミニオンが3%を超えたため）。RNNoiseは現行モデル（D-019）のまま据え置く。`rnnoise_data_little.c`への切替（CPUは約1/3減る見込み、音質は未評価）は、Windows実機の実測で3.5%を超えた場合の選択肢として残す。

### 理由
- シフターと同じ扱い（D-014）で、固定遅延は機能の代償として明示する。Sonarを経路から外せば、Sonar自身の処理と仮想デバイスの遅延がなくなる。

### 影響
- ノイズ除去ONでシフター休止時の合計が50msを超える場合がある。遅延をさらに縮める必要が出たら、フレーミング遅延の短縮（plan.md 8.5）を検討する。

## D-026: 声量はこもり軽減より優先する。EQは声量を下げず、プリセットは出力ゲインで補う

- 日付: 2026-10-01
- 状態: 採用（ユーザー確認済み）

### 背景
- ユーザーはSonarのEQを本アプリのEQプリセット（A2・A3）で置き換えたい。A2・A3は低域を大きく削る（ローシェルフ26Hz −18dB）ため、ゲインを足さないと発話のK特性ラウドネスが下がりうる。
- T-014の実録音（raw_A、発話2.53秒）で測ると、A2・A3をゲイン0dBでかけたときのK特性は生より+0.4dB（RMSは−0.2 / −0.6dB）で、現在のSonarのEQ近似は+2.4dB（RMS +2.2dB）。

### 決定
- 声量（発話のK特性ラウドネス）は、こもりの軽減より優先する。
- ノイズ除去は、発話のK特性ラウドネスを生より0.5dBを超えて下げない（T-014の暫定基準をこの決定の一部とする）。
- EQは声量を下げない。プリセットは、5バンドの後に掛ける「EQ出力ゲイン」（−12〜+12dB、0.1dB刻み、既定+2.0dB＝A2の値）で補う。A2・A3のプリセット適用時の値は+2.0dB（K特性が生より+2.4dB、Sonar近似の+2.4〜2.5dBに近い）。「EQなし」はEQをOFFにするだけで、OFFのときは出力ゲインもかからない。
- 出力ゲインは設定ファイルへ`eqOutputGainDb`として保存する（キーがなければ既定の+2.0dB、非有限値も既定、範囲外は±12dBへ丸める）。選択中のプリセットは保存せず、EQのON/OFFと5バンド・出力ゲインの値から毎回導出する。

### 理由
- 声が小さくなる副作用は、こもりが減る利点より聴感への悪影響が大きい。ラウドネスの指標（K特性）は声の低い成分の重みを小さくするため、RMSより聴感に近い。
- 出力ゲインをEQの一部にすると、EQのON/OFFの20msクロスフェード・OFF時のビット一致・バイパス時の扱い（D-020）をそのまま保てる。別の段（層1のゲイン）を使うと、ユーザーのゲインと混ざり、プリセットが値を上書きしてしまう。
- 保存を値だけにすると、選択と値が食い違う状態が生まれない。

### 影響
- 出力ゲインを足すぶん、EQで持ち上げた信号が最終段の±1.0クリップに近づく。全体バイパス中はリミッターを通らない（D-018）。実録音（raw_A、ピーク−13.1dBFS）ではA2・A3（+2.0dB込み）のピークが−10.1 / −9.8dBFS（ノイズ除去ON）で、クリップしない。生のピークが約−3dBFSを超える大きな声では、バイパス中にクリップしうる。
- 出力ゲインの既定はA2の値（+2.0dB。2026-10-01、ユーザー承認）。バンドの初期値もA2なので、初回にEQスイッチをONにしただけでA2になる。キーのない既存の設定の出力ゲインも+2.0dBになるが、EQは既定OFFで未使用のため許容する。
- 声量の実測値の表と根拠はdocs/progress.md。

## D-027: ヘリウム・ミニオン・ジャイアントの値、プリセットの声量補正ゲイン、層1ピッチ±24

- 日付: 2026-10-01
- 状態: 採用（ユーザーの試聴で決定。T-018の第1段）

### 背景
- ユーザー報告: ヘリウム（移調0・フォルマント1.6）・ミニオン（+8・1.4）・ジャイアント（-6・0.75）は効果が弱い。調査では名目値どおりに効いており（f0比±1%、包絡±3%）、弱く聞こえる原因は名目値そのものだった（progress.md）。試聴サンプル（各プリセット4〜6候補）を作って選んでもらった。
- 移調を上げると声が小さくなる（調査: ミニオン+10で約-3.6dB、+12で-3.4〜-5.1dB）。声量はこもり軽減より優先する（D-026）。

### 決定
- 値（試聴結果）: ヘリウム 移調+9・フォルマント1.6、ミニオン +12・1.6、ジャイアント -6・0.75（変更なし）。3種とも「足りない点なし」。ジャイアントはユーザーが「st+6.fm0.75」と書いたが、試聴した候補に+6はなく、現行値（-6・0.75）を指すと解釈した（Managerの解釈。値は変えていない）。
- 声量の補正ゲイン: `PresetSpec`にプリセットごとの`gainDb`を持たせる。ヘリウム+0.5dB、ミニオン+3.0dB、ジャイアント+1.0dB、ロボット+3.0dB（下記の追記）、ほかは0dB（トークボックスはキャリア側に固定の補正を持つ）。ユーザーの録音（raw_A、発話区間2.53秒）を`--process-wav --float`で各プリセットに通し、`--compare`のK特性とRMSで元の声との差を測り、補正後の差が±1dB以内になる0.5dB刻みの値にした（補正前のK特性の差: ヘリウム-0.5、ミニオン-2.8、ジャイアント-1.4dB。補正後 K / RMS: -0.0 / -0.3、+0.2 / -0.2、-0.4 / +0.3dB。表はprogress.md）。
- 掛ける位置: 層2・リバーブ・層1のゲインの後、リミッターの前。層1のゲイン（`gainSmoothed`、50ms）とは別の補間器`presetGainSmoothed`（乗算の補間、20ms）で掛ける。20msは声質の切替（層2のクロスフェード・シフターのフェード）と同じ長さ。プリセットの切替時に補正が変わってもクリックは出ない（E9の56通り全件合格）。UIのゲインスライダーの値は変えない（E11bで、層1のゲイン+6dBがプリセットによらず+6dBであることを確認）。
- 層1ピッチ: ±12 → ±24半音（`kMaxLayer1PitchSemitones`）。根拠: (1) ±24は実用範囲（99Hzの声で+24は約400Hz、-24は約25Hz。調査で精度・CPU・健全性とも問題なし）、(2) CPUは移調量に依存せず約1.5%（層1の±24との組み合わせも1.4〜1.5%）、(3) 下げ方向の精度に限界がある（下記）。±36は動作するが実用性が低く、採らない。保存済みの設定（±12以内）は移行不要。Engineと`PitchShifter`は範囲に縛られず、層1+プリセットの合計は-30〜+36まで動く（NaN/Infなし・確保0回・ピーク≤1.0をE7・E8で確認）。

### 理由
- 補正を層1のゲインとは別の項にしたのは、ユーザーのゲインの値をプリセットが書き換えないため（D-026の出力ゲインと同じ理由）。補間器も別にして20msにしたのは、最初に層1のゲインへ足して共通の50msで掛けたところ、ノイズ除去ONのミニオン→トークボックス（N9b。背景100%）が最悪比1.542で限界1.5を超えたため（切替の最中に補正が+0.7dB前後残り、トークボックスの立ち上がりの過渡を持ち上げた。補正0dBなら1.42）。声質の切替と同じ20msにすると、N9bの最悪比は従来どおり1.422（ノーマル→トークボックス）、E9は1.301になった。限界は緩めていない。
- 補正値は1人の声（raw_A、f0中央値99Hz）の実測で決めた。声の高さ・声質で移調後の声量の落ち方は変わりうる。実機で聴いて違和感があれば値だけ調整する（表の1か所）。

### 影響
- 移調精度（P3）: 下げ方向で出力が約100Hz未満になると、期待値に対する相対誤差が1%を超える（220Hz正弦で-18が+1.36%、-25が-3.3%）。Signalsmith Stretchの量子化誤差で、Hzで見ると一定（220Hz入力の-30〜-1半音で最大1.7Hz、STFTの1ビン8.33Hzの約1/5）。上げ方向は+36まで±0.6%以内。合格基準は、期待値が100Hz以上なら従来どおり±1%、100Hz未満は±2.0Hz（実測最大に約15%の余裕）とし、100Hz以上の従来のケースは緩めていない。880Hz入力の-30（出力156Hz）は-1.46%（2.3Hz）で1%を超えるが、層1+プリセットの下限（-30）に高い声（880Hz）が入る組み合わせは使われないため、テストに入れずここに記録する。
- P4（フォルマント保持）: +24は従来の合格基準を満たす。-24は出力のf0が40Hz未満になり、合成母音でf0比が-6〜-8%ずれ、sも乱れる（f0=150Hzで1.715、100Hzで1.15）。f0の誤差は上記の量子化誤差と同じで、sの測定は出力のf0を基準に倍音の位置を取るため、f0の数Hzのずれが測定を狂わせる（測定の限界）。実音声では、包絡の移動量が-36〜+36で中央値0.99〜1.05だった。このため-24は合格基準ではなく、実測値の悪化を検出する上限（P4aはf0比±8%・s±0.8、P4bはf0比±10%・s±0.25）で判定する。
- 補正ゲインを足すぶん、出力のピークが増える。実録音では最大で+3.0dB（ミニオン）、出力ピークは-11.8dBFSで、リミッター（閾値-1dB）には届かない。入力のピークを+12dBした試験（ピーク-1.1dBFS）でも、ミニオンの最大のゲイン低下は約0.3dBだった。
- ロボットの補正（追記、Managerの依頼）: リングモジュレーションは声の各成分を和と差の側帯波に分けて振幅を半分にするため、声量が約3dB下がっていた（補正前のraw_A: K特性 -3.3 / RMS -3.1dB）。ロボットにも+3.0dBを足した（補正後 K -0.3 / RMS -0.1dB、区間ごとのRMSの差は-0.3〜0.0dB。+3.5dBなら+0.2 / +0.4）。出力ピークは-13.9→-10.9dBFS（入力-13.1）。入力を+12dB（ピーク-1.1dBFS）にした試験で初めてリミッターが約1.5dB効き、+10dB（ピーク-3.1dBFS）では-1dBFS超が2サンプルだけで、過度には働かない。ケロケロ・エコー・ノーマルは変更しない。
