# 設計判断記録 (ADR)

設計判断、採用理由、変更履歴を記録する。新しいエントリは末尾に追加する（古い順）。

## 記録フォーマット

```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-001: 入力と出力を別々のAudioIODeviceとして開く

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は入出力デバイス間のクロックずれ補正（リングバッファ + 可変レートリサンプリング）と、サンプルレート差の吸収を求めている。

### 決定
- `juce::AudioDeviceManager`の一体型デバイスを使わず、`AudioIODeviceType::createDevice(出力名, "")`と`createDevice("", 入力名)`で2つのデバイスを開き、別々のコールバックで動かす。DSPは出力コールバック内で出力レートで行う。

### 理由
- JUCE 9.0.2のWASAPI実装（`juce_WASAPI_windows.cpp`）は、入出力一体型のとき1スレッドで両方を回し、共通のサンプルレートを要求する（共通レートがないと`open()`がエラーを返す）。低遅延モードではOS側のレート変換も無効になる。この構成ではクロックずれを補正する場所がない。
- DSPを出力側で行うと、処理時間の揺れがリングバッファで吸収され、出力の締め切りに対して必要なサンプル数だけを処理できる。

### 影響
- デバイスの一覧取得・開閉・エラー処理をアプリ側で実装する必要がある（AudioDeviceManagerの機能を使わない）。

## D-002: ピッチシフターをチェーン先頭に置き、不要時は休止する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は処理順を「層2 → 層1」とし、ピッチシフトのみ層1と層2を合算して1回で処理するとしている。位置は明記されていない。
- 48kHz・Signalsmith Stretchの実測で、移調の有無にかかわらず1コアの約1.5%を使う（Xeon 2.1GHz、ブロック20〜120ms）。ノーマル時1%未満の要件を満たせない。

### 決定
- シフターをチェーン先頭に置き、合計移調量0かつフォルマント係数1のときは休止する。休止⇔稼働は20msのクロスフェードでつなぐ。休止中は遅延がシフター分だけ短くなる（遅延は一定にしない）。

### 理由
- 単声の信号の方がシフト品質が良い、ロボットの変調周波数が層1ピッチで変わらない、ケロケロの補正量を加工前の声から求められる。
- 遅延を一定に保つ案（休止中も同じ長さの遅延線を通す）も検討した。OBSで音声のオフセットを固定値で合わせる用途では一定の方が扱いやすいが、変動幅は最大40ms程度で、プリセット切り替え時にしか変わらない。通話・自分の声のモニタリングでは短い方が有利なため、短くする方を選んだ。どちらの案も切り替え用の状態遷移が必要で、実装量は同程度。

### 影響
- 表示レイテンシはプリセットと層1ピッチで変わる。

## D-003: ブロック長をデバイス遅延から毎回計算する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は「50ms以内に収まる最も長い設定を採用する」としている。Signalsmith Stretchの遅延はブロック長にほぼ等しい（実測）。一方、デバイス遅延は低遅延モード対応の有無で数ms〜20ms以上と大きく変わる。

### 決定
- デバイスを開いた時点で、ブロック長 = clamp(50ms − デバイス遅延 − リングバッファ目標 − 2ms, 20ms, 40ms) とする。

### 理由
- 固定値では、低遅延モード非対応のデバイス（VB-CABLE等が該当する可能性がある）で50msを超えるか、対応デバイスで品質を余らせる。20msの下限は男性の声の基本周期の2周期分を窓に含めるため。

### 影響
- 環境によっては50msを超える。その場合はUIに表示し、実測値を報告する。

## D-004: 開発環境での検証範囲

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 開発はLinuxのクラウド環境で行い、Windows実機・オーディオデバイスがない。

### 決定
- DSPコアとリングバッファのロジックを、JUCEのGUI・デバイス部から分離したライブラリにし、Linuxで単体テスト（オフライン模擬を含む）を行う。アプリ本体もLinuxでコンパイルし、Xvfb上でUIのスクリーンショットを確認する。
- Windowsの.exeはGitHub Actions（windows-latest、MSVC、`/MT`）でビルドし、同じテストをWindowsでも実行する。
- 実機での動作・聴感・1時間連続動作はユーザーが行う。判定用に統計ログを出力する。

### 理由
- 実機がない状態で「動作確認済み」とできる範囲を、合否を返すチェックで最大化するため。

### 影響
- WASAPI固有の挙動（低遅延モードの可否、デバイス抜去時の通知）は実機でしか確認できず、未検証として報告する。

## D-005: DSPコアをINTERFACEライブラリにする

- 日付: 2026-09-28
- 状態: 採用

### 背景
- JUCEモジュールはINTERFACEライブラリで、リンクしたターゲットごとにJUCEのソースがコンパイルされる。DSPコアをSTATICライブラリにすると、JUCEのソースがライブラリとexeの両方でコンパイルされ、重複定義やODR不一致の危険がある。

### 決定
- `vc_core`をINTERFACEライブラリにし、DSPソースとjuce_core/juce_audio_basics/juce_dsp/signalsmith-stretchをINTERFACEで持たせる。アプリとテストがそれぞれリンクする。

### 理由
- テスト実行ファイルはvc_coreしかリンクしないため、DSPソースがGUI・デバイスのヘッダをincludeするとテストのビルドが失敗し、層の分離が機械的に担保される。代償はDSPソースを2回コンパイルすることだけで、ファイル数が少ないため許容できる。

### 影響
- docs/spec.mdの「DSPコアを静的ライブラリにする」記述をINTERFACEライブラリに改める。

## D-006: リングバッファの充填量は読み出し直後に測る

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 読み出し前に測って目標 = max(Bi, Bo) + 2ms で制御すると、Bi ≈ Bo のとき読み出し前の充填量の最小値が1回の読み出し量を下回り、起動直後にアンダーランが数回起きる。

### 決定
- 充填量は出力コールバックの読み出し直後に測る。表示するリングバッファ遅延は「平滑化した読み出し直後の充填量 + Bo/2」（時間平均）とする。目標の式は仕様のまま据え置く。

### 理由
- 読み出し直後に測れば最小値 ≥ max(Bi, Bo) − Bi/2 + 2ms > 0 が保証される。目標の式は必要最小値よりBi/2ほど保守的だが、実機のスケジューリングの揺れが未測定のため余裕を残す。

### 影響
- 実機ログでアンダーランが0のまま推移するなら、目標を下げる余地がある。

## D-007: 出力段のリミッターをCompressorとクリップで構成する

- 日付: 2026-09-28
- 状態: 採用

### 背景
- `juce::dsp::Limiter`は常に閾値-10dB・4:1の圧縮とメイクアップをかけ、ゲイン0dBでも小さい音を約+2.9dB持ち上げる。原指示の「ゲインを上げても0dBFSを超えないための簡易リミッター」は、通常時に音を変えない透過的なものを意図している。

### 決定
- `juce::dsp::Compressor`（閾値-1dB、比100、アタック0.1ms、リリース100ms）の後に`FloatVectorOperations::clip`で±1.0に制限する。

### 理由
- どちらもJUCEの既存部品で、閾値以下では音を変えず、クリップで0dBFSを超えないことが保証される。

### 影響
- 閾値を超える瞬間のアタック内はクリップが働くため、極端に大きな入力では歪みが出る。音割れよりは小さい。

## D-008: リバーブの混合量はJUCEの内部倍率を打ち消して渡す

- 日付: 2026-09-28
- 状態: 採用

### 背景
- `juce::Reverb`はdryLevelに×2、wetLevelに×3の内部倍率を掛ける。「wet = r、dry = 1 − r」をそのまま渡すと、r ≈ 0 でdryが+6dBになる。

### 決定
- `Parameters`には wetLevel = r/3、dryLevel = (1 − r)/2、width = 1 を渡す。仕様の「wet = r、dry = 1 − r」は出力に掛かる線形ゲインとして解釈する。

### 理由
- 仕様の意図（rで残響の混合量だけが変わり、r = 0で原音と同じ音量）を実現する変換であり、仕様変更ではない。

### 影響
- なし。

## D-009: デバイス異常時の扱いと多重起動

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 原指示は切断時のエラー表示と復帰時の再接続を求めているが、片方だけの異常、起動時に保存済みデバイスがない場合、多重起動について記載がない。

### 決定
- 片方のデバイスだけが異常になっても両方を閉じ、両方が揃ってから両方を開き直す。
- 起動時に保存済みのデバイスが見つからない場合は既定デバイスへ切り替えず、エラーを表示して再試行を続ける。
- 多重起動を禁止する（`moreThanOneInstanceAllowed() = false`）。

### 理由
- 両方を閉じる方式は状態の組み合わせが減り、クロックずれ補正の再初期化も1か所で済む。
- 保存済みデバイスへの自動復帰を優先するため、勝手に既定デバイス（物理スピーカー等）へ声を流さない。配信中に意図しない出力先へ声が出る事故を防ぐ。
- 多重起動するとデバイスを二重に開き、同じVB-CABLEへ2系統の音が混ざる。

### 影響
- 保存済みデバイスを使わなくなった場合は、利用者がドロップダウンで選び直す必要がある。

## D-010: 最終出力の異常値検査はバイパス中も行う

- 日付: 2026-09-28
- 状態: 採用

### 背景
- 仕様ではバイパス時に処理チェーン全体（NaN検査を含む）を入力の素通しに置き換える。入力デバイス側から異常値が来た場合に検査がなくなる。

### 決定
- 最終出力の非有限値検査はバイパス中も常に行う。エラー表示は docs/design.md 6章に従い、異常値は10秒間、デバイス異常は復旧まで表示する。

### 理由
- 検査のコストは1ブロックの走査だけで、VB-CABLE経由で配信・通話アプリへ異常値を渡す事故を防げる。

### 影響
- なし。

## D-011: 利用形態は個人利用のみ（配布なし）

- 日付: 2026-09-28
- 状態: 採用

### 背景
- JUCE 9はAGPLv3と商用ライセンスのデュアルライセンスで、exeを第三者へ配布する場合はソースのAGPL公開かJUCEのライセンスが必要になる。

### 決定
- ユーザーの確認により、本アプリは個人利用のみとし配布しない。JUCEはAGPLv3の条件下で使用し、商用ライセンスは取得しない。

### 理由
- 配布しない限りAGPLv3の公開義務は生じないため、追加の対応は不要。

### 影響
- 将来配布する場合は、この判断を見直してライセンスを再検討する。READMEのライセンス節にその旨を記載する。
