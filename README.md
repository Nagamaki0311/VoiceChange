# VoiceChange

Windows向けリアルタイムボイスチェンジャー（単一の.exe）。物理マイク・SteelSeries Sonar等の仮想入力デバイスの音声を加工し、VB-CABLE経由でDiscordやOBSへ渡す。

想定するチェーン:

```
物理マイク → (Sonar等の前段処理) → VoiceChange → VB-CABLE (CABLE Input) → Discord / OBS
```

詳細な仕様はdocs/spec.md、UIはdocs/design.md、実装計画はdocs/plan.md、設計判断の経緯はdocs/decisions.mdを参照する。開発フロー（Manager/Planner/Developer/Reviewer等の役割分担）はAGENTS.mdを参照する。

## 動作要件

- Windows 10 / 11（64bit）。
- [VB-CABLE](https://vb-audio.com/Cable/)を別途インストールしておくこと（本アプリには同梱しない）。未インストールの場合、起動時に検出できなかった旨のダイアログを表示する。
- 入力元は物理マイクに限らず、SteelSeries Sonar等の仮想入力デバイスも区別なく選べる。

## 実装済みの機能

- 入力・出力を別々のWASAPIデバイスとして開き、クロックずれをリングバッファと可変レートリサンプラで補正する（Sonar等の仮想入力やVB-CABLEとのレート差を吸収）。
- 層1（音響卓）: ゲイン（-20〜+20dB）、ピッチ（-12〜+12半音、フォルマント保持）、リバーブ。出力はコンプレッサー（閾値-1dB・比100）と±1.0のクリップで保護する（バイパス時は±1.0のクリップのみ。D-018）。
- 層2（択一のプリセット）: ノーマル / エコー / ヘリウム / ミニオン / ジャイアント / ケロケロ / ロボット / トークボックス。全体ON/OFF（バイパス）は20msでクロスフェードする。
- デバイスの選択と設定の保存、VB-CABLE未検出の案内、タスクトレイ常駐、デバイス抜去時のエラー表示と自動再接続、60秒ごとの統計ログ。
- **遅延**: ピッチシフターが休止している間（ノーマル・エコー・ロボット・トークボックスで層1ピッチ0）は50ms目標。シフター稼働中（ヘリウム・ミニオン・ジャイアント・ケロケロ、または層1ピッチ≠0）は約120ms加わり、合計130〜160ms程度になる（docs/decisions.md D-014。低い声の音程精度のため）。OBSでは映像と口の動きが合わない場合、音声の詳細プロパティの「同期オフセット」（ms）で映像に合わせる。

### 未検証事項（Windows実機でしか確認できないもの）

開発環境はLinuxで、次はテストできていない。下記の「実機での確認手順」でユーザーが確認する。

- WASAPI固有の挙動（低遅延モードの可否、バッファ長、デバイスのサンプルレート変更）と実測の遅延。
- VB-CABLE経由でDiscord・OBSへ声が渡ること、各プリセットの聴感。
- デバイス抜去・再接続、トレイ操作。
- 実機での1時間連続動作（アンダーラン・遅延・メモリ・CPU）。Linuxではデバイスなしのオフライン模擬（tests/LongRunTests.cpp、音声時間3600秒。リングバッファ→全プリセットの処理チェーンをプリセット・ピッチ・バイパスを切り替えながら通す）でNaN/Inf・ピーク・アンダーラン・音声スレッドのアロケーションを確認している。

## .exeの入手

GitHub Actionsの`build`ワークフローの実行結果ページ下部「Artifacts」から`VoiceChange-windows`をダウンロードして展開する（`VoiceChange.exe`のみ、インストール不要。CIの最新の成功実行を使う）。自分でビルドする場合は下記のビルド手順を参照する。

## ビルド手順

### Windows（配布用）

Visual Studio 2022（Desktop development with C++）とCMake 3.25以上が必要。

```
cmake -S . -B build -A x64
cmake --build build --config Release
```

生成物は`build/VoiceChange_artefacts/Release/VoiceChange.exe`。MSVCランタイムは静的リンク（`/MT`）するため、VC++ 再頒布可能パッケージのインストールなしで動作する（CIの`dumpbin /dependents`検査で確認している）。

### Linux（開発用、配布対象外）

開発はLinux上で行い、DSPコア（`vc_core`、GUI・デバイス非依存のINTERFACEライブラリ）とテストの検証、UIのXvfb上でのスクリーンショット確認に使う。ALSA・X11系・freetype・fontconfigの開発パッケージが必要（`.github/workflows/build.yml`のlinuxジョブ参照）。

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

依存ソース（JUCE / signalsmith-stretch / signalsmith-linear / RNNoise本体 / RNNoiseのモデル）はCMakeの`FetchContent`で取得する。RNNoiseはCMakeファイルを持たないため、本リポジトリのCMakeLists.txtが`vc_rnnoise`（Cの静的ライブラリ）としてビルドする。ネットワークなしでローカルの取得済みソースを使う場合は次のように指定する（RNNOISE_MODELはモデルのtar.gzを展開したディレクトリで、`src/rnnoise_data.c`を含む）。

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_JUCE=<JUCEのパス> \
  -DFETCHCONTENT_SOURCE_DIR_SIGNALSMITH-STRETCH=<stretchのパス> \
  -DFETCHCONTENT_SOURCE_DIR_SIGNALSMITH-LINEAR=<linearのパス> \
  -DFETCHCONTENT_SOURCE_DIR_RNNOISE=<rnnoise v0.2のパス> \
  -DFETCHCONTENT_SOURCE_DIR_RNNOISE_MODEL=<モデルを展開したパス>
```

モデル（21MB）は`-DVC_RNNOISE_MODEL_DOWNLOAD_DIR=<ディレクトリ>`を指定すると、tar.gzをそこへ保存し、SHA256が一致すれば再取得しない（CIはこのディレクトリを`actions/cache`で保存する）。

## 実機での確認手順

CIとLinux上のテスト（トレイ非対応・実デバイスなし）では検証できない項目。Windows実機で以下を確認する。

### セットアップと聴感確認

1. [VB-CABLE](https://vb-audio.com/Cable/)のZIPをダウンロードして展開し、`VBCABLE_Setup_x64.exe`を管理者として実行してインストールし、Windowsを再起動する。
2. `VoiceChange.exe`を起動する。入力はマイク（またはSonar等の仮想入力）、出力は`CABLE Input`を選ぶ（初回は出力が自動で`CABLE Input`になる）。
3. Discord: ユーザー設定 > 音声・ビデオ > 入力デバイスを`CABLE Output`にする。OBS: 音声入力キャプチャのデバイスを`CABLE Output`にする。自分の声をモニターしたい場合は、Windowsの録音デバイス`CABLE Output`のプロパティ > 聴く > 「このデバイスを聴く」で再生先を指定する。
4. 各プリセット（ノーマル・エコー・ヘリウム・ミニオン・ジャイアント・ケロケロ・ロボット・トークボックス）を順に選び、声が期待どおり変わること、プリセット切り替え時とON/OFF切り替え時にクリック音が出ないこと、ゲイン最大付近で音が割れないことを聴いて確認する。フォルマント効果は低い男性の声（100Hz以下）では弱く聞こえることがある（下記「フォルマント補正の効果とPSOLA方式の検討」参照）。

### トレイ常駐

1. アプリを起動し、ウィンドウの閉じるボタン（またはEscキー）を押す。ウィンドウが消え、タスクトレイにアイコンが現れることを確認する。初回の格納時だけ「タスクトレイで動作を続けています。アイコンをクリックするとウィンドウを再表示します。」という通知が出ることを確認する（2回目以降は出ない）。
2. トレイアイコンにマウスを乗せ、ツールチップが`VoiceChange — ON（<プリセット名>）`（エフェクトOFF中は`VoiceChange — OFF（バイパス）`）と表示されることを確認する。
3. トレイアイコンを左クリックしてウィンドウが再表示されることを確認する。
4. トレイアイコンを右クリックし、「ウィンドウを表示」「エフェクトをOFFにする（ONにする）」「終了」の3項目（区切り線つき）が出ることを確認する。「エフェクトをOFF(ON)にする」を選び、ウィンドウを表示した状態でエフェクト全体ON/OFFトグルが連動して切り替わることを確認する。
5. 「終了」を選ぶとアプリが完全に終了し、トレイアイコンも消えることを確認する。

### デバイス抜去と再接続

1. アプリ起動中に、使用中のUSBマイク（またはUSBオーディオインターフェース）を抜く。
2. ウィンドウ下部の状態表示に「入力デバイスが切断されました。再接続を試みています（n秒経過）…」が出て、遅延の数値が`—`になり、入力欄が赤枠になることを確認する。トレイアイコンにも赤いバッジが付き、ツールチップが「VoiceChange — エラー：入力デバイス切断」になることを確認する。
3. マイクを挿し直す。デバイス一覧の変更通知が来ればほぼ即座に、来なくても2秒間隔のリトライで数秒以内に自動再接続され、状態表示が「正常に動作しています」に戻ることを確認する。
4. 出力側（USBスピーカー・USBオーディオインターフェース等）を抜き差しして同様に確認する（「出力デバイスが切断されました…」）。
5. 保存済みデバイスを未接続のままアプリを起動し、既定デバイスへ勝手に切り替わらずエラー表示のまま再試行を続けること、その後デバイスを接続すると自動的に開くことを確認する（D-009）。

### 1時間連続動作テストとログの見方

1. VoiceChangeを起動中なら終了し、`%APPDATA%\VoiceChange\VoiceChange.log`を削除してから起動する（起動時に1MB超なら自動で作り直される）。
2. Discord通話またはOBS録音を実際に動かし、マイクに向かって話したり黙ったりしながら、プリセットを途中で数回切り替えつつ、60分以上放置する。最初の30分はノーマル、次の30分はトークボックスなど重い効果、のようにCPUを両方見られるようにする。
3. ログは60秒ごとに1行追記される。書式: `t=<経過秒>s latencyMs=<遅延ms> fillMs=<リングバッファ充填量ms> underruns=<回数> overruns=<回数> speedPpm=<速度比補正ppm> cpu=<CPU使用率%> memMB=<メモリ使用量MB>`。
4. 判定基準（docs/spec.md「パフォーマンス要件」を元にした案。実機の実測値を見てユーザーと合意して確定する）:

| 項目 | 基準（案） |
|---|---|
| `underruns` | 開始1分以降に増えない |
| `latencyMs` | 変動が2ms以内（同じプリセット・ピッチの区間で比べる。シフター稼働の切り替えでは約120ms変わる） |
| `memMB` | 1時間の増加が1MB以内 |
| `cpu` | ノーマルで1%未満、ヘリウムやトークボックス等の重い効果で5%以下 |

5. 基準を外れた場合は、ログ全体、使用デバイス、プリセットの操作履歴を添えて報告する。

ログの`cpu`はオーディオコールバック全体の負荷（指数移動平均で平滑化）で、テストのCPU参考値（`Engine::process`のみ、Linux・概算）とは定義が違う。実機の値はテストの値より大きくなり得る。

## フォルマント補正の効果とPSOLA方式の検討

ヘリウム・ミニオン・ジャイアントは、Signalsmith Stretchの移調とフォルマント係数（`setFormantFactor(係数, true)`）で実現している。測定はtests/EffectsTests.cpp（F1〜F3）とtests/ShifterTests.cpp（P4a/P4b）で、48kHz・合成母音（/a/: F1=730・F2=1090・F3=2440Hz）の定常1.5秒を16384点FFTで解析する。s（包絡スケール）は出力の倍音包絡が入力に対して周波数軸上で何倍に動いたか（1.0で不動、フォルマント係数と同じなら期待どおり）。

| 測定 | 条件 | f0比（期待） | s（期待） | 判定 |
|---|---|---|---|---|
| F1 ヘリウム | f0=150Hz | 1.0000（1.0000） | 1.585（1.60） | 合格基準を満たす |
| F2 ミニオン | f0=150Hz | 1.5879（1.5874） | 1.375（1.40） | 合格基準を満たす |
| F3 ジャイアント | f0=150Hz | 0.7091（0.7071） | 0.750（0.75） | 合格基準を満たす |
| F1 ヘリウム | f0=100Hz（特性確認） | 1.0000（1.0000） | 1.070（1.60） | 失敗判定なし |
| F2 ミニオン | f0=100Hz（特性確認） | 1.6062（1.5874） | 1.455（1.40） | 失敗判定なし |
| F3 ジャイアント | f0=100Hz（特性確認） | 0.7041（0.7071） | 0.725（0.75） | 失敗判定なし |
| P4a +5半音 | f0=150Hz、層1ピッチでフォルマント保持 | 1.3447（1.3348） | 1.010（1.0） | 合格基準を満たす |
| P4a -5半音 | 同上 | 0.7475（0.7492） | 0.995（1.0） | 合格基準を満たす |
| P4b +5半音 | f0=100Hz（特性確認） | 1.3434（1.3348） | 1.165（1.0） | D-015の基準値と同じ |
| P4b -5半音 | 同上 | 0.7597（0.7492） | 0.795（1.0） | D-015の基準値と同じ |

- 合格基準はf0比±1%・s±10%（F1〜F3はsが期待値±10%、P4aはs=1.0±10%）。f0=150Hzでは全件が基準内に収まった。
- f0=100Hzのような低い声では、Signalsmith Stretchはf0を最大約1.4%ずらし、フォルマントの動きも目標から外れる（docs/decisions.md D-013・D-015）。ヘリウムのf0=100Hzでは、フォルマントが目標1.6倍のところ1.07倍しか動かなかった。P4bとして測ったD-015の基準値（f0誤差最大+1.4%、s=0.795/1.165）からは悪化していない。
- ヘリウム（移調0・フォルマント係数1.6）に`setFormantBase`を与える実験（Signalsmith Stretch単体、48kHz、合成母音、T-005で実施。一時テストは削除済み）。sは目標1.6に対する実測値。f0比はどの条件でも1.0000。

| f0 | (a) 既定（自動推定） | (b) setFormantBase(真のf0) | (c) setFormantBase(ピッチ検出器の推定値) |
|---|---|---|---|
| 80Hz | s=1.075 | s=1.000 | s=1.000（推定80.00Hz） |
| 100Hz | s=1.070 | s=1.000 | s=1.000（推定100.00Hz） |
| 150Hz | s=1.585 | s=1.000 | s=1.000（推定150.01Hz） |

  `setFormantBase`を与えるとフォルマントは全く動かなくなり（s=1.0）、150Hzでも既定より悪化する。低いf0でヘリウムが効かない問題は改善しないため、ピッチ検出器の推定値を渡す実装は採用しない（D-015の追加実験と同じ結論）。

- D-013: ブロック長20〜40msではf0が1〜5%ずれる。D-014: ブロック長を120msに固定して解決した（代償としてシフター稼働中の遅延が約120ms増える）。
- **PSOLA方式（またはそれに近い時間領域の手法）へ差し替えるかどうかは、ユーザーの判断事項である。** D-014・D-015の時点でユーザーはSignalsmith Stretchの継続を選んでおり、今回のT-005の測定でもf0=150Hzでは仕様の基準を満たしたため、実装は差し替えていない。低い男性の声（f0=100Hz以下）でヘリウム・ミニオン・ジャイアントのフォルマント効果が弱く感じられる場合は、聴感で判断して差し替えを検討する。

## CPU使用率（概算の参考値）

Linux（開発環境、Release）で、48kHz・480サンプルブロック・10秒の合成母音を`Engine::process`に通し、処理時間÷音声時間を測った概算値（tests/EngineTests.cppのE10、失敗判定なし。マシン・負荷で変わる）。実機（Windows）のCPU使用率はAudioIOの出力コールバック内の値を統計ログの`cpu=`で確認する。

| プリセット | CPU（処理時間÷音声時間） |
|---|---|
| ノーマル | 0.04% |
| エコー | 0.09% |
| ヘリウム | 1.32% |
| ミニオン | 1.54% |
| ジャイアント | 1.50% |
| ケロケロ | 2.27% |
| ロボット | 0.09% |
| トークボックス | 2.63% |

ノーマルは1%未満、トークボックス等の重い効果も5%以下で、docs/spec.mdの要件を満たしている。ピッチシフターを使うプリセットは1〜2.3%程度。

## ノイズ除去の客観指標（合成信号、T-011）

Linux（開発環境、Release）で、tests/MicTests.cppのカテゴリMic（`GateImpact`）が合成信号（合成母音・ピンク/白色雑音・クリック）に対して測った実測値。閾値はdocs/plan.md 8.3の暫定値のまま。N5aの判定条件は、初回実装後に背景70%のみへ限定した（100%は0%側のクリックが床近くまで下がっていて比が縮み、−9.8〜−13.4dBとなるため。Managerが承認済み）。0%・100%は参考値として記録する。N5aの−12.0dBの判定には浮動小数点の丸めの分として0.05dBの数値許容がある（下表）。合成信号はRNNoiseの実音声での挙動を代表しない（docs/plan.md 8.5）。実録音での評価はT-014・T-015。

当初のパラメータ（インパクト抑制のホールド15ms、ゲートを閉じる側の余裕+6dB）ではN5b（立ち上がり）が閾値を外れたため、パラメータを**ホールド3ms、閉じる側の余裕+8dB**に調整した（D-022・D-023）。表は調整後の値で、括弧内は調整前。

| ID | 内容 | 閾値（暫定） | 実測（調整前） |
|---|---|---|---|
| N1 | SNR改善量（発話1秒・無音1秒、ピンク雑音SNR 10dB、背景70%） | +6dB以上 | 区間全体 +9.68dB（入力7.22→出力16.91dB）、発話区間のみ +6.64dB（同じ） |
| N2 | 無声区間の残留雑音（ピンク雑音 −30dBFS、入力雑音比） | 50%で−12dB以下、100%で−25dB以下、単調減少 | 0/25/50/75/100%: 0.0 / −12.0 / −55.8 / −56.6 / −57.2dB（同じ。RNNoise自体が合成雑音を−56dB抑える） |
| N2（ゲートの効果） | 発話後の無音での、背景100%と50%の差（SNR 10dBの白色雑音） | −12dB以下（ゲートの減衰量は最大18dB） | −18.0dB（3回とも。同じ） |
| ゲートの閉じる割合 | 発話の後の無音（0.3秒以降）で閉じているサンプルの割合（ピンク雑音、SNR 10dB） | 1割以上 | 84%（調整前 46%）。ピンク雑音−30dBFS単独の7秒では 約40% → 約93% |

### 既知の限界・確認項目

- **N9b**: プリセット切替56通り（3条件、切替位相7・11サンプル）は全件合格（最悪比 1.422 / 1.420、限界1.5との余裕0.078）。**ゲートの効果は判定に現れていない**（背景50%と100%で最悪比が同一）。1.422はRNNoise処理後の信号を基準にすることで上がった値で、ゲートによるものではない。
- **雑音床の回復が遅い**: 雑音床の下限（−90dBFS）から3dB/秒でしか上がらないため、デジタル無音を3秒続けた後に発話し、その後−60dBFSの雑音になると、ゲートが閉じるまで8.7秒かかる（最初から雑音があれば0.22秒）。マイクのミュート明けなどで起きうる。実録音で確認する項目（D-022）。
- **変異テストで検出できない変異**: 雑音床の−90dBFS下限、遅い包絡の−80dBFS下限、`latched = min`（再検出時に深い減衰を保つ側）、ゲートを閉じるときの150msのフェード。いずれもテストを追加していない。
- ミニオンのノイズ除去ON増分は+3.06ポイントで、目標の3%（D-025）をわずかに超える（RNNoise本体が支配的。EQ込みはT-012のEQ9で確定）。

| 項目 | 採用 |

| ビルド | MSVC、`/MT`（GitHub Actions windows-latest） |

### 選定理由

- JUCEは`IAudioClient3`による「WASAPI共有低遅延モード」に対応しており、他アプリと干渉しない共有モードのまま低遅延を実現できる。
- GC（ガベージコレクション）のない言語（C++）で音声スレッドを完全に制御できる。
- DSP部品・GUI・デバイス管理が単一フレームワーク（JUCE）で揃い、依存が少ない。
- Signalsmith Stretchは高品質なピッチシフトとフォルマント操作をMITライセンスで提供する。

### 使わないもの

- **Rubber Band**: GPLライセンスのため、AGPLv3/商用デュアルのJUCEと組み合わせても配布条件が複雑になる。MITのSignalsmith Stretchで要件（移調・フォルマント操作）を満たせるため採用しない。
- **WASAPI排他モード**: 排他モードで開いたデバイスは他アプリが同時に使えなくなる。本アプリはSonar等の前段処理やDiscord/OBSと並行して動く前提のため、共有モード（低遅延モード優先、フォールバックで通常モード）のみを使う。
