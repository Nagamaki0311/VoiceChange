# VoiceChange

Windows向けリアルタイムボイスチェンジャー（単一の.exe）。物理マイク・SteelSeries Sonar等の仮想入力デバイスの音声を加工し、VB-CABLE経由でDiscordやOBSへ渡す。

想定するチェーン:

```
物理マイク → (Sonar等の前段処理) → VoiceChange → VB-CABLE (CABLE Input) → Discord / OBS
```

詳細な仕様はdocs/spec.md、UIはdocs/design.md、実装計画はdocs/plan.md、設計判断の経緯はdocs/decisions.mdを参照する。開発フロー（Manager/Planner/Developer/Reviewer等の役割分担）はAGENTS.mdを参照する。

## 動作要件

- Windows 10 / 11（64bit）。
- [VB-CABLE](https://vb-audio.com/Cable/)を別途インストールしておくこと（本アプリには同梱しない）。未インストールの場合、起動時に検出できなかった旨のダイアログを表示する。
- 入力元は物理マイクに限らず、SteelSeries Sonar等の仮想入力デバイスも区別なく選べる。

## 実装済みの機能

- 入力・出力を別々のWASAPIデバイスとして開き、クロックずれをリングバッファと可変レートリサンプラで補正する（Sonar等の仮想入力やVB-CABLEとのレート差を吸収）。
- 層1（音響卓）: ゲイン（-20〜+20dB）、ピッチ（-12〜+12半音、フォルマント保持）、リバーブ。出力はコンプレッサー（閾値-1dB・比100）と±1.0のクリップで保護する（バイパス時は±1.0のクリップのみ。D-018）。
- 層2（択一のプリセット）: ノーマル / エコー / ヘリウム / ミニオン / ジャイアント / ケロケロ / ロボット / トークボックス。全体ON/OFF（バイパス）は20msでクロスフェードする。
- **マイク処理**（ノイズ除去とEQ）: 入力の直後、層1・層2より前にかかり、全体ON/OFF（バイパス）の対象外（D-020）。入力行の「マイク処理」ボタンで開く別ウィンドウで設定する（下記「マイク処理の使い方」）。ノイズ除去はRNNoiseベースで、ONにすると声の遅れが約30ms増える。
- デバイスの選択と設定の保存、VB-CABLE未検出の案内、タスクトレイ常駐、デバイス抜去時のエラー表示と自動再接続、60秒ごとの統計ログ。
- **遅延**: ピッチシフターが休止している間（ノーマル・エコー・ロボット・トークボックスで層1ピッチ0）は50ms目標。シフター稼働中（ヘリウム・ミニオン・ジャイアント・ケロケロ、または層1ピッチ≠0）は約120ms加わり、合計130〜160ms程度になる（docs/decisions.md D-014。低い声の音程精度のため）。OBSでは映像と口の動きが合わない場合、音声の詳細プロパティの「同期オフセット」（ms）で映像に合わせる。

### 未検証事項（Windows実機でしか確認できないもの）

開発環境はLinuxで、次はテストできていない。下記の「実機での確認手順」でユーザーが確認する。

- WASAPI固有の挙動（低遅延モードの可否、バッファ長、デバイスのサンプルレート変更）と実測の遅延。
- VB-CABLE経由でDiscord・OBSへ声が渡ること、各プリセットの聴感。

- 実機での1時間連続動作（アンダーラン・遅延・メモリ・CPU）。Linuxではデバイスなしのオフライン模擬（tests/LongRunTests.cpp、音声時間3600秒。リングバッファ→全プリセットの処理チェーンをプリセット・ピッチ・バイパスを切り替えながら通す）でNaN/Inf・ピーク・アンダーラン・音声スレッドのアロケーションを確認している。

## マイク処理の使い方

メインウィンドウの入力行の右にある「マイク処理」ボタン（ノイズ除去かEQのどちらかがONのときは、ランプが緑で塗りつぶされる）で、マイク処理ウィンドウを開く。閉じるボタンかEscで閉じる（メインをトレイへ格納したときも一緒に閉じる）。変更はすぐに音へ反映され、設定にも保存される（適用・キャンセルのボタンはない）。

- **ノイズ除去**: スイッチでON/OFF。「背景ノイズ」は空調やファンなど続く雑音を抑える強さ（既定65%。50%を超えると、話していない間の音も下げる）、「インパクト」はキーボードやクリックなど短い音を抑える強さ（既定15%）。スライダーはダブルクリックで初期値に戻る。ONにすると声の遅れが約30ms増える。
- **EQ**: スイッチでON/OFF。5つのバンドを、有効チェック・タイプ（ピーキング / ローシェルフ / ハイシェルフ / ローカット［ハイパス］/ ハイカット［ローパス］）・周波数（20〜20000Hz）・ゲイン（±18dB。ローカット・ハイカットでは使わない）・Q（0.10〜10.00）で設定する。5バンドの下の「出力ゲイン」（±12dB、0.1dB刻み、既定+2.0dB＝A2の値）は、5バンドの後で声の音量を上げ下げする（EQがOFFのときはかからない）。上のグラフは設定の周波数特性（5バンドの和＋出力ゲイン。読み取り専用。有効なバンドの位置に番号付きの印が出る）。
- **数値欄の操作**: 欄をクリック（またはTabで移動）すると入力できる。Enterで確定、Escで取り消し（ウィンドウは閉じない）、Tabで確定して次の欄へ。全角の数字や単位（Hz・dB）、`1.2k`（= 1200Hz）も使える。範囲外は端へ丸められ、数値として読めない入力は元の値に戻る。ホイールと↑↓キーで微調整できる（周波数とQは約6%＝1/12オクターブずつ、ゲインは0.5dBずつ）。ドラッグでは値は変わらない。
- **EQプリセット**: 「EQなし」（EQをOFFにするだけ。バンドの値と出力ゲインはそのまま残る）・「A2」（自然なクリアさ）・「A3」（声の輪郭がはっきり）。A2・A3は5バンドと出力ゲイン（+2.0dB。声を小さくしないための補正）を書き換えてEQをONにする。選択中のプリセットは保存せず、EQのON/OFFと値から毎回決まる（値を変えると、どのボタンも選択されない「カスタム」になる）。メインのマイク処理ボタンのツールチップには「EQ OFF / EQ A2 / EQ A3 / EQ カスタム」が出る。
- **元に戻す**: プリセットを選んだ直後だけ使え、プリセットを選び始める前の状態（5バンドの値・出力ゲイン・EQのON/OFF）に戻す。続けて別のプリセットを選んでも、戻り先は最初の状態のまま。バンドの値か出力ゲインを変えるか、ウィンドウを閉じると使えなくなる（EQスイッチの切り替えでは使えなくならない）。
- **全体ON/OFFとの関係**: エフェクト全体をOFFにしても、マイク処理はかかったまま（副文は「マイク処理のみ適用中（バイパス）」）。

### 設定ファイルの項目

`%APPDATA%\VoiceChange\VoiceChange.settings`（XML）に、次のキーで保存される。範囲外の値は範囲の端へ、数値として読めない値やキーがない項目は初期値に丸められる。初回起動時のノイズ除去・EQはOFF。

| キー | 内容 | 範囲・初期値 |
|---|---|---|
| `nrEnabled` / `eqEnabled` | ノイズ除去 / EQのON/OFF | 0か1。初期値0 |
| `nrBackground` / `nrImpact` | 背景ノイズ / インパクトの強さ | 0〜1（UIの0〜100%）。初期値0.65 / 0.15 |
| `eqOutputGainDb` | EQの出力ゲイン | -12〜+12（dB）。初期値+2.0（キーがない既存の設定もこの値になる） |
| `eqBand{1..5}On` | バンドの有効 | 0か1 |
| `eqBand{1..5}Type` | タイプ | `peak` / `lowshelf` / `highshelf` / `lowcut` / `highcut`（不明な名前は`peak`） |
| `eqBand{1..5}Hz` | 周波数 | 20〜20000 |
| `eqBand{1..5}GainDb` | ゲイン | -18〜+18 |
| `eqBand{1..5}Q` | Q | 0.1〜10 |

EQの初期値のバンドはA2（ローシェルフ26Hz −18dB Q0.48 / ピーキング216Hz +1.0dB Q0.75 / ピーキング450Hz −2.5dB Q1.00 / ピーキング2500Hz +4.0dB Q0.70 / ハイシェルフ5741Hz +2.0dB Q1.00）。出力ゲインの初期値は+2.0dB（A2の値。A3のプリセットも+2.0dB）なので、初回にEQスイッチをONにするとA2になる。

## .exeの入手

GitHub Actionsの`build`ワークフローの実行結果ページ下部「Artifacts」から`VoiceChange-windows`をダウンロードして展開する（`VoiceChange.exe`のみ、インストール不要。CIの最新の成功実行を使う）。自分でビルドする場合は下記のビルド手順を参照する。

## ビルド手順

### Windows（配布用）

Visual Studio 2022（Desktop development with C++）とCMake 3.25以上が必要。

```
cmake -S . -B build -A x64
cmake --build build --config Release
```

生成物は`build/VoiceChange_artefacts/Release/VoiceChange.exe`。MSVCランタイムは静的リンク（`/MT`）するため、VC++ 再頒布可能パッケージのインストールなしで動作する（CIの`dumpbin /dependents`検査で確認している）。

### Linux（開発用、配布対象外）

開発はLinux上で行い、DSPコア（`vc_core`、GUI・デバイス非依存のINTERFACEライブラリ）とテストの検証、UIのXvfb上でのスクリーンショット確認に使う。ALSA・X11系・freetype・fontconfigの開発パッケージが必要（`.github/workflows/build.yml`のlinuxジョブ参照）。

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

UIの見た目は、Xvfb上で`VoiceChange --screenshot <path.png>`（メインウィンドウ）と`VoiceChange --screenshot-mic <path.png>`（マイク処理ウィンドウ）を実行するとPNGに書き出して終了する。表示する設定は設定ファイル（Linuxでは`$HOME/VoiceChange/VoiceChange.settings`）で決まる。日本語の描画にはNoto Sans CJK JPが必要。

依存ソース（JUCE / signalsmith-stretch / signalsmith-linear / RNNoise本体 / RNNoiseのモデル）はCMakeの`FetchContent`で取得する。RNNoiseはCMakeファイルを持たないため、本リポジトリのCMakeLists.txtが`vc_rnnoise`（Cの静的ライブラリ）としてビルドする。ネットワークなしでローカルの取得済みソースを使う場合は次のように指定する（RNNOISE_MODELはモデルのtar.gzを展開したディレクトリで、`src/rnnoise_data.c`を含む）。

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_JUCE=<JUCEのパス> \
  -DFETCHCONTENT_SOURCE_DIR_SIGNALSMITH-STRETCH=<stretchのパス> \
  -DFETCHCONTENT_SOURCE_DIR_SIGNALSMITH-LINEAR=<linearのパス> \
  -DFETCHCONTENT_SOURCE_DIR_RNNOISE=<rnnoise v0.2のパス> \
  -DFETCHCONTENT_SOURCE_DIR_RNNOISE_MODEL=<モデルを展開したパス>
```

モデル（21MB）は`-DVC_RNNOISE_MODEL_DOWNLOAD_DIR=<ディレクトリ>`を指定すると、tar.gzをそこへ保存し、SHA256が一致すれば再取得しない（CIはこのディレクトリを`actions/cache`で保存する）。

## 実機での確認手順

CIとLinux上のテスト（トレイ非対応・実デバイスなし）では検証できない項目。Windows実機で以下を確認する。

### セットアップと聴感確認

1. [VB-CABLE](https://vb-audio.com/Cable/)のZIPをダウンロードして展開し、`VBCABLE_Setup_x64.exe`を管理者として実行してインストールし、Windowsを再起動する。
2. `VoiceChange.exe`を起動する。入力はマイク（またはSonar等の仮想入力）、出力は`CABLE Input`を選ぶ（初回は出力が自動で`CABLE Input`になる）。
3. Discord: ユーザー設定 > 音声・ビデオ > 入力デバイスを`CABLE Output`にする。OBS: 音声入力キャプチャのデバイスを`CABLE Output`にする。自分の声をモニターしたい場合は、Windowsの録音デバイス`CABLE Output`のプロパティ > 聴く > 「このデバイスを聴く」で再生先を指定する。
4. 各プリセット（ノーマル・エコー・ヘリウム・ミニオン・ジャイアント・ケロケロ・ロボット・トークボックス）を順に選び、声が期待どおり変わること、プリセット切り替え時とON/OFF切り替え時にクリック音が出ないこと、ゲイン最大付近で音が割れないことを聴いて確認する。フォルマント効果は低い男性の声（100Hz以下）では弱く聞こえることがある（下記「フォルマント補正の効果とPSOLA方式の検討」参照）。

### トレイ常駐

1. アプリを起動し、ウィンドウの閉じるボタン（またはEscキー）を押す。ウィンドウが消え、タスクトレイにアイコンが現れることを確認する。初回の格納時だけ「タスクトレイで動作を続けています。アイコンをクリックするとウィンドウを再表示します。」という通知が出ることを確認する（2回目以降は出ない）。
2. トレイアイコンにマウスを乗せ、ツールチップが`VoiceChange — ON（<プリセット名>）`（エフェクトOFF中は`VoiceChange — OFF（バイパス）`）と表示されることを確認する。
3. トレイアイコンを左クリックしてウィンドウが再表示されることを確認する。
4. トレイアイコンを右クリックし、「ウィンドウを表示」「エフェクトをOFFにする（ONにする）」「終了」の3項目（区切り線つき）が出ることを確認する。「エフェクトをOFF(ON)にする」を選び、ウィンドウを表示した状態でエフェクト全体ON/OFFトグルが連動して切り替わることを確認する。
5. 「終了」を選ぶとアプリが完全に終了し、トレイアイコンも消えることを確認する。

### デバイス抜去と再接続

1. アプリ起動中に、使用中のUSBマイク（またはUSBオーディオインターフェース）を抜く。
2. ウィンドウ下部の状態表示に「入力デバイスが切断されました。再接続を試みています（n秒経過）…」が出て、遅延の数値が`—`になり、入力欄が赤枠になることを確認する。トレイアイコンにも赤いバッジが付き、ツールチップが「VoiceChange — エラー：入力デバイス切断」になることを確認する。
3. マイクを挿し直す。デバイス一覧の変更通知が来ればほぼ即座に、来なくても2秒間隔のリトライで数秒以内に自動再接続され、状態表示が「正常に動作しています」に戻ることを確認する。
4. 出力側（USBスピーカー・USBオーディオインターフェース等）を抜き差しして同様に確認する（「出力デバイスが切断されました…」）。
5. 保存済みデバイスを未接続のままアプリを起動し、既定デバイスへ勝手に切り替わらずエラー表示のまま再試行を続けること、その後デバイスを接続すると自動的に開くことを確認する（D-009）。

### 1時間連続動作テストとログの見方

1. VoiceChangeを起動中なら終了し、`%APPDATA%\VoiceChange\VoiceChange.log`を削除してから起動する（起動時に1MB超なら自動で作り直される）。
2. Discord通話またはOBS録音を実際に動かし、マイクに向かって話したり黙ったりしながら、プリセットを途中で数回切り替えつつ、60分以上放置する。最初の30分はノーマル、次の30分はトークボックスなど重い効果、のようにCPUを両方見られるようにする。
3. ログは60秒ごとに1行追記される。書式: `t=<経過秒>s latencyMs=<遅延ms> fillMs=<リングバッファ充填量ms> underruns=<回数> overruns=<回数> speedPpm=<速度比補正ppm> cpu=<CPU使用率%> memMB=<メモリ使用量MB> nr=<ON|OFF> eq=<ON|OFF>`。`nr`・`eq`はノイズ除去・EQのON/OFFで、CPUの基準をONのときとOFFのときで区別して判定するために出す。
4. 判定基準（docs/spec.md「パフォーマンス要件」を元にした案。実機の実測値を見てユーザーと合意して確定する）:

| 項目 | 基準（案） |
|---|---|
| `underruns` | 開始1分以降に増えない |
| `latencyMs` | 変動が2ms以内（同じプリセット・ピッチの区間で比べる。シフター稼働の切り替えでは約120ms変わる） |
| `memMB` | 1時間の増加が1MB以内 |
| `cpu` | `nr=OFF eq=OFF`のとき、ノーマルで1%未満、ヘリウムやトークボックス等の重い効果で5%以下。`nr=ON`または`eq=ON`のときは、その増分が3.5%以下（目標。D-025） |

5. 基準を外れた場合は、ログ全体、使用デバイス、プリセットの操作履歴を添えて報告する。

ログの`cpu`はオーディオコールバック全体の負荷（指数移動平均で平滑化）で、テストのCPU参考値（`Engine::process`のみ、Linux・概算）とは定義が違う。実機の値はテストの値より大きくなり得る。

## 実録音と比較する手順（T-014）

本アプリのノイズ除去・EQを、実際のマイク音声とSteelSeries Sonarの処理後の音声に対して、オフラインで比較する。ツールはテスト用実行ファイル`VoiceChangeTests`のモードで、アプリ本体には入らない（`VoiceChangeTests`をビルドすれば使える。Linuxで動作確認済み。Windowsでの実行は未検証）。録音ファイルは個人の音声データなので、リポジトリにはコミットしない。

注意:
- ファイル名・フォルダ名はASCIIにする。引数はUTF-8として読むが、Windowsのコマンドライン引数（ANSIコードページ）での非ASCIIの扱いは未検証。
- Windowsのコンソールで日本語のレポートを読むときは、先に`chcp 65001`を実行するか、ファイルへリダイレクトする（`> report.txt`）。
- 既知の限界: 1/3オクターブの帯域端（63Hz・8kHz付近）は、FFTのビンを重なり幅で按分する近似。`detectSegments`の閾値は経験値の粗い判定。`writeWav`は既存ファイルを先頭へ戻して切り詰めるが、その成否は確認していない（M1fの上書きの確認のみ）。いずれも精密なテストは未整備。

### 1. 録音する（OBS）

1. OBSで、物理マイク（フィルタなしの生音声）とSonarの仮想マイク（Sonarの処理後）を、別々の音声トラックで同時に録音する（「設定 → 出力 → 録画」で音声トラック1・2を有効にし、「音声ミキサー → 詳細プロパティ」で各ソースのトラックを割り当てる）。同時録音にすると、両者を同じ時間軸で比較できる（別テイクだと「同じ信号を通した差」ではなく統計的な比較になる）。
2. 台本（約90秒）: 無音10秒 → 普通に話す30秒 → 話さずに打鍵10秒 → 話しながら打鍵20秒 → 無音10秒 → 小声と語尾を伸ばす発話10秒。空調・PCファンは普段どおりにする。各区間の開始・終了時刻をメモしておく（下の区間ファイルになる）。
3. 録画ファイルから各トラックの音声を48kHzのWAVへ変換する（例: `ffmpeg -i rec.mp4 -map 0:a:0 -ac 1 -ar 48000 -c:a pcm_f32le raw.wav`、`-map 0:a:1`で`sonar.wav`）。OBSのAAC圧縮の影響で、約-100dBFS以下の比較は不正確になる。

### 2. 本アプリの処理を通す（`--process-wav`）

```
VoiceChangeTests --process-wav <in.wav> <out.wav> [--bg 0.65] [--impact 0.15] [--nr on|off]
                 [--eq on|off|a2|a3|sonar] [--eq-gain <dB>] [--settings <VoiceChange.settings>]
                 [--segments <区間ファイル>] [--trace <csv>] [--float]
```

- WAVを読み、WAVのサンプルレートでEngine（プリセット ノーマル、ゲイン0）に通して書き出す。設定は、既定（ノイズ除去ON、背景0.65・インパクト0.15、EQ OFF）→ `--settings`（アプリの設定ファイル。Linuxでは`$HOME/VoiceChange/VoiceChange.settings`、Windowsでは`%APPDATA%\VoiceChange\VoiceChange.settings`）→ 各オプション、の順に上書きされる。`--bg`・`--impact`は0〜1（アプリの0〜100%）、`--nr`は`on`・`off`、`--eq`は下記の値だけを受け付け、それ以外は終了コード2のエラー。入力と出力に同じファイルは指定できない。
- `--eq`: `on`は設定ファイル（なければ初期値）のバンドでON、`a2`（自然なクリアさ）・`a3`（輪郭はっきり。どちらも本アプリのプリセット。出力ゲイン+2.0dB込み）・`sonar`（現在のSonarのEQの5バンド近似。出力ゲインなし）はバンドと出力ゲインを置き換えてON。`--eq-gain`（-12〜12）は出力ゲインだけを上書きする（ゲインを振って声量を測るため）。
- 出力は、ノイズ除去の遅延（48kHzで1440サンプル = 30ms。表示される）を取り除いて入力と同じ長さ・同じ位置に揃える。既定は16bit PCM（聴き比べ用）。**`--compare`に渡すWAVは`--float`（32bit float）で書き出す**: 16bitの量子化雑音は約-90dBFSで、それ以下の残留雑音は測れない。
- 区間ごとの「ゲートが開いていた割合」と「インパクト抑制が働いていた割合」を表示する（区間は`--segments`、省略時は入力の自動判定）。`--trace`は10msごとのCSV（時刻、入力・出力のRMS[dBFS]、ゲート開放の割合、インパクト抑制の割合）。

### 3. 比較する（`--compare`）

```
VoiceChangeTests --compare <raw.wav> <sonar.wav> <ours.wav> [--segments <区間ファイル>] [--sonar-segments <区間ファイル>]
```

`ours.wav`は`--process-wav --float`の出力（rawから作る）。同時録音ならrawとsonarの遅れを相互相関で揃える（相関0.3以上）。別テイクなら揃えず、sonar自身のエネルギーで区間を自動判定する（`--sonar-segments`で時刻を与えてもよい）。

区間ファイル（台本の時刻）: 1行に「開始秒 終了秒 種類」。種類は`silence`（無音）・`speech`（発話）・`impact`（打鍵のみ）・`speech+impact`（発話＋打鍵）。`#`以降はコメント。省略時は音声のエネルギーで自動判定する（雑音床+20dB以上が120ms以上続けば発話、短ければ打鍵、雑音床+10dB以下が300ms以上続けば無音。粗い判定なので、台本の時刻があればそちらを使う）。

出力される指標（表）:

| 指標 | 読み方 |
|---|---|
| 区間ごとのRMS・ピーク [dBFS] | 打鍵の行に、本アプリ処理によるピークの減衰量（ours - raw）が付く |
| 無声区間の残留雑音 RMS | 小さいほど静か。RMSは大きなフレームに引っ張られるため、10msフレームの中央値と、-100dBFS未満のフレームの割合（デジタル無音）も併記。`*`は-100dBFS未満（AAC圧縮の影響で不正確） |
| 発話区間のレベル（RMS） | 非加重。生との差（ours - raw）が声量の目安。区間の種類が`speech+impact`の区間は、声量の指標（RMS・K特性）に含まれない（`speech`の区間だけ） |
| 発話区間のK特性重み付けパワー | ITU-R BS.1770のK特性（ゲートなしの簡易版）。生との差が主指標。暫定基準: ノイズ除去を通しても生に対して-0.5dBより下がらない（発話を小さくしていない） |
| 発話と残留雑音の比（SNR） | 発話RMS - 無声区間RMS。無声区間がデジタル無音のときは下限（`>`） |
| 1/3オクターブスペクトル（63Hz〜8kHz） | 無声区間は帯域パワー、発話区間は長時間平均。「差」は絶対値（レベル差を含む）、「形」は全帯域の平均差を引いた値（EQの形） |

無声区間または発話区間の合計が1秒未満のときは注意が出る（1秒未満の窓での過大解釈をしない）。

### 4. 聴き比べる

発話レベルを揃えたraw・sonar・oursの3本をユーザーが聴き比べて、採否と調整値を決める。指標は判断材料で、合否は聴感で決める（目標値はdocs/plan.mdのT-015）。

### 既知の限界・確認項目

- **N9b**: プリセット切替56通り（3条件、切替位相7・11サンプル）は全件合格（最悪比 1.422 / 1.420、限界1.5との余裕0.078）。**ゲートの効果は判定に現れていない**（背景50%と100%で最悪比が同一）。1.422はRNNoise処理後の信号を基準にすることで上がった値で、ゲートによるものではない。
- **雑音床の回復が遅い**: 雑音床の下限（−90dBFS）から3dB/秒でしか上がらないため、デジタル無音を3秒続けた後に発話し、その後−60dBFSの雑音になると、ゲートが閉じるまで8.7秒かかる（最初から雑音があれば0.22秒）。マイクのミュート明けなどで起きうる。実録音（T-014の初回評価）では、デジタル無音（Sonarの無音）の直後に雑音のある生音声を続けると、ゲートが最初に閉じるまで7.6秒かかり（生音声だけなら0.46秒）、8秒間の閉じていた時間は0.09秒（生音声だけでは1.86秒）だった。Sonarなど前段のノイズ除去がデジタル無音を作る構成では実際に起きる（D-022、docs/progress.md T-014）。
- **変異テストで検出できない変異**: 雑音床の−90dBFS下限、遅い包絡の−80dBFS下限、`latched = min`（再検出時に深い減衰を保つ側）、ゲートを閉じるときの150msのフェード。いずれもテストを追加していない。

## EQの客観指標（合成信号、T-012）

## 技術スタック

| 項目 | 採用 |
|---|---|
| 言語 | C++20 |
| フレームワーク | JUCE 9.0.2（CMake、FetchContentでタグ固定） |
| ピッチ/フォルマント | Signalsmith Stretch 1.4.0（依存: signalsmith-linear 0.6.4） |
| ノイズ除去 | RNNoise v0.2（組み込みモデル`rnnoise_data-0b50c45`。Cの静的ライブラリ`vc_rnnoise`、CPU別最適化なし） |
| ビルド | MSVC、`/MT`（GitHub Actions windows-latest） |

### 選定理由

- JUCEは`IAudioClient3`による「WASAPI共有低遅延モード」に対応しており、他アプリと干渉しない共有モードのまま低遅延を実現できる。
- GC（ガベージコレクション）のない言語（C++）で音声スレッドを完全に制御できる。
- DSP部品・GUI・デバイス管理が単一フレームワーク（JUCE）で揃い、依存が少ない。
- Signalsmith Stretchは高品質なピッチシフトとフォルマント操作をMITライセンスで提供する。

### 使わないもの

- **Rubber Band**: GPLライセンスのため、AGPLv3/商用デュアルのJUCEと組み合わせても配布条件が複雑になる。MITのSignalsmith Stretchで要件（移調・フォルマント操作）を満たせるため採用しない。
- **WASAPI排他モード**: 排他モードで開いたデバイスは他アプリが同時に使えなくなる。本アプリはSonar等の前段処理やDiscord/OBSと並行して動く前提のため、共有モード（低遅延モード優先、フォールバックで通常モード）のみを使う。
